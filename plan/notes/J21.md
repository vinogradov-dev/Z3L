# J21 — What was measured

## What was measured

- The owner's endpoint `https://opencode.ai/inference/openai/v1` with
  `deepseek-v4.1-flash` produced no answer; the panel read "the assistant's request ended
  without an answer".
- `z3l.log` carried `thread 'agent-request' panicked ... ureq-3.5.2/src/unversioned/
  transport/mod.rs:517: uri scheme is https, provider is Rustls but feature is not enabled:
  rustls`.
- `cargo tree -p mcp -e features -i ureq` shows `native-tls`, `native-tls-no-default` and
  `native-tls-webpki-roots` enabled, and no `rustls`.
- ureq 3.5's `TlsProvider` defaults to `Rustls` and its own documentation says the setting
  "is never picked up automatically"; the `native-tls` feature compiles the connector but does
  not choose it.

## What was decided

- `OpenAi::new` names `TlsProvider::NativeTls` on the one shared agent, beside the request
  timeout. This is ADR 0189's transport, now selected rather than assumed.
- The panic is not caught. The next provider mismatch would hide behind the same vague
  sentence; the worker's death stays the last-resort sentence it always was.
- A unit test reads the agent's own `TlsConfig` and asserts the provider, so the selection
  cannot disappear without a red test.

## What was ruled out

- Enabling ureq's `rustls` feature: ring and aws-lc-rs compile C, which AGENTS.md §2 forbids.
- `catch_unwind` around the request: it would turn a configuration defect into a message that
  says nothing about the cause.
- A network test in the suite: the live probe was run by hand instead — a fake key against
  opencode.ai answered `HTTP 401`, so TLS reaches the host — and the committed test reads the
  config, which is the fact that broke.
