# O7 — The folder is the package, and one version names the rows it depends on

The folder is the package, and one version names the rows it depends on

## What was measured

- `crates/catalog/src/write.rs` already had the one writer: the lock, `save_item`, the atomic file
  write, and the "record first, manifest last" order. `directory.json` was read by the loader
  (`FolderSource::packages`) and written by nobody, so a package could be edited but never enabled.
- `FolderSource::snapshot` did the whole load inline, including the per-package manifest, registry and
  record reads. Nothing could ask "would this directory load?" without touching disk.
- `ManifestWire` carried `id`, `name`, `package_version` and no `requires`, although `§12` and `§16`
  both name one.
- `crates/project/src/lib.rs` (the entry's second `files:` path) is unreachable from `catalog`: both
  crates are layer L2 and neither depends on the other, so `project::write_and_rename` cannot be the
  copy helper. The hint is wrong and was not used.
- `fs::copy` copies content and permissions and no timestamp, which is what "the copy is the file"
  needs: a re-serialization through `ItemWire` would rewrite `package_version` and make two
  directories disagree about one package.

## Decisions

- `load(root, packages)` is the loader lifted out of `snapshot`: one function reads a chosen set, so
  `connect`, `disconnect` and `import` are refused by the same rows a reload would use, before any
  file is written.
- A requirement names a *package*, not its rows: `requires: [{ id, name, package_version }]`. The
  kinds, properties and families a package resolves through live inside it, so one content version
  names them all; a per-row requirement would need each registry row to know which package owns it,
  which nothing in the model tracks. `docs/domain/nomenclature.md` §12 was rewritten to say this,
  because its "registry revisions: kinds, properties, families" allowed the second reading.
- A requirement is checked against the whole connected set, never against load order, and
  `package_version` is a floor (`<`, not `!=`).
- Two connected folders that claim one number are refused by the loader, not by the duplicate record
  check three files later: same `ItemId`s, but the sentence names both packages.
- Export and import copy the folder tree file by file (`tree_files` walks with its own stack and
  refuses a symbolic link), then write the manifest last. The manifest is one of the files the
  reader's stamp watches, so a reader pointed at the copy never sees a package that is missing one.
- Import lands the copy **unlisted**, checks it with `load`, and writes `directory.json` last: the
  stamp moves once, when the whole package is in place. A copy the loader refuses — or a copy that
  fails halfway — is removed again, so an inert folder cannot make the next import fail.
- `connect` and `disconnect` are idempotent and return the revision the window polls; a disconnect
  that would strand a `requires` is refused by the candidate load, naming the package that needs it.
- A package name is one path component (`plain_name`): it comes from a supplier's folder as often as
  from a person, and it is joined onto the directory root.

## Ruled out

- **Following symbolic links while copying** — a link back into the package copies forever.
- **Writing `directory.json` before the copy** — a window polling the folder would list a package
  whose files are half there.
- **Validating the incoming package on its own** — a record may resolve a `Ref` through a package
  that stays behind, so a valid package would be refused alone; it is checked beside what is
  connected.
- **`WriteError::UnknownPackage` kept as a second sentence for a missing folder** — one refusal
  (`MissingPackage`) names the folder and the name, and `save_item` uses it too.
- **A separate crate for copying a folder** — two files of std-only code against a new layer-map row,
  a new `PROJECT.md` entry and a duplicated atomic write (the same reasoning as O6).
