# P25 — Two writers in one checkout are one at a time

Two writers in one checkout are one at a time

## What was measured

The entry was filed on 2026-11-21 saying the tool takes no lock inside a checkout. That sentence was
already stale: `apply` did create `plan/.lock` through `create_new`, so the two renames were
serialised. It was taken too late — *after* `changed()` and the gate, and every verb had read
`plan/BACKLOG.md` and derived its id long before `apply` was called. The cycle a writer owns is four
steps — read the plan, splice the lines it owns, validate the whole result, write — and only the
last one was inside the lock, so two `task add` runs computed the same next free id and the later
write replaced the earlier entry while the gate stayed green.

`Lock` was 16 lines in `state-contract/src/cli/write.rs` with no test at all, and `--dry-run`
returned before it was taken.

## Decisions

- **The lock is taken at a verb's entrance.** `write::run_with`, `write::state` and `write::file`
  acquire it before they read a plan file — before the stream refusal, which reads `plan/STATUS.md` —
  and hold it until the verb returns. `apply` no longer acquires it; it takes the guard as an
  argument instead, so a verb that forgets to acquire one does not compile.
- **A second writer waits two seconds, then refuses.** `PATIENCE = 2 s`, polled every 10 ms. Waiting
  is what makes both writes land, which is the outcome the entry asks for first; the bound is what
  keeps a stale `plan/.lock` from hanging a session forever, and the refusal names the file and the
  two things a person can do about it. A verb's own cycle is tens of milliseconds, so the wait
  almost always ends inside the first poll.
- **A `--dry-run` holds the lock too.** It writes no plan content, but its diff is a promise about
  what would land, and a reading another session is mid-replacement makes the preview wrong. The
  guard's drop removes the file, so a dry run still leaves the tree as it found it.
- Recorded as ADR 0224, which amends the `plan/.lock` consequence of ADR 0085; the map row names the
  new anchors.

## Ruled out

- **Compare-and-swap in `apply`** (re-read each file under the lock, refuse when it differs from what
  the verb read): it needs no long hold and would also catch a worktree race, but it turns the second
  writer's command into a refusal the caller has to repeat, and the entry asks for both writes to
  land when they can.
- **`flock`/`fcntl` on the lock file.** `std::fs` has no file lock in safe Rust; it would need `unsafe`
  FFI (`AGENTS.md` §4.4 forbids `unsafe`) or a `-sys` crate, and `create_new` is already a
  cross-process test-and-set with no dependency.
- **Refusing at once with no wait** (the previous behaviour, one line up the call): a person running
  two commands, or a batch that files two entries, meets a refusal that is not about their plan.
- **An in-process mutex.** Two shells are two processes; a mutex in `state-contract` reaches neither.

## Evidence the test is not decoration

The race test (`two_writers_in_one_checkout_both_land`, four threads behind one barrier) was run
five times against a build whose `Lock::acquire_within` returned without creating the file: failed
5/5, each time with one entry lost. With the lock at the entrance it passes 3/3, and
`the_writer_lock_covers_the_cycle_and_is_released_afterwards` pins the wait, the refusal sentence and
the absent file after a normal write, a refused write and a dry run.
