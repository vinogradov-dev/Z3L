## What was measured

- `crates/ui/src/inventory.rs` holds 57 rows and U94 marked seven of them `Place::ContextMenu`:
  `node.rename`, `node.delete`, `node.delete.many`, `node.duplicate`, `node.group`, `node.ungroup`,
  `node.component.convert_to_group`. The tree's four menu builders in `scene_tree.rs` (608 lines)
  offered five of those commands plus five entries that are session state, not commands: hide/show,
  lock/unlock, isolate, show all, add child and open/close product.
- `Row.applies` was `Applies::Context | Always` and no code read it: the node a capability acts on was
  nowhere in the table, so no surface could filter by node kind.
- The viewport already owned the right button: `document.rs` pans on
  `dragged_by(PointerButton::Secondary)`, and a drawing draft commits on `clicked_by(Secondary)`.
  egui sets `clicked_by` only inside its click distance, so click-versus-drag is the engine's split
  and needs no second threshold.
- `Chrome` carried the two panel rectangles, the ribbon band and the ribbon's open list, and `covers`
  is the one question the viewport asks before a pick. A floating surface outside it is a click that
  picks through a menu (ADR 0080).

## Decisions

- `Applies::Context` gained the node it acts on (`ActsOn`), so a menu filters the inventory by the
  node under the pointer instead of keeping a second list. Rows that no menu draws name their scope
  too, because the card (U93) and the tool card (U97) filter the same column.
- The list is one `Vec<Entry>` of both kinds: a capability (id, label, enabled, reason) and a session
  entry. A locked node keeps its edits visible and refused with the sentence that says why.
- `TreeAction` moved to `node_actions.rs` as `NodeAction`, and the popup dispatches through the same
  `Editor::apply_node_action`, so the two surfaces share the action enum as well as the words.
- A right click does not select: it acts on the node under the pointer, as a tree row's menu does,
  and the entry carries its own id into the command.
- Empty space owns the document-level view action only (*Show all*), because creation is armed from
  the ribbon with its parameters (ADR 0117, 0119).
- `node.rename` and `node.delete.many` lost `Place::ContextMenu`: a menu carries no text entry, and a
  batch delete belongs to the key and the palette (ADR 0112).

## Ruled out

- Deriving the scope from an id's prefix (`panel.*` → a panel): a string namespace is a second table
  the compiler cannot check; the context column already existed and ADR 0117 makes context data.
- Keying the session entries in the inventory: the gate resolves a row to a `CommandSpec`, and hide,
  lock, isolate and show all dispatch no command by design (ADR 0065).
- Selecting the node on a right click: the tree row does not, and a selection that moves a card under
  the pointer is a second change the person did not ask for.
- A batch *Delete selection* entry on a multi-selection: the menu names one node, and the key and the
  palette already own the batch with its question (ADR 0112).
- Keeping the view entries in the tree and only the commands in the list: that is the fourth
  register ADR 0117 ends, and the popup would then silently lack *Hide* and *Lock*.

## The cheap path

One line in `crates/engine/src/commands.rs`'s neighbourhood would have saved the read: a sentence in
`Row`'s doc saying *the context column is the node a capability acts on* — `Applies` already existed
with exactly that name and carried no payload, and finding that out cost the inventory read plus the
U94 note. The second line is in `plan/map.md`'s scene-tree row, which still named `view_menu` as the
row's menu: a map row that names the function that builds the list would have sent the session
straight at the five builders instead of grepping.

## For the strategy

Route a task that touches `crates/ui` through the design skill's *surfaces* table before the source:
it names the surface and its owner in one row and would have replaced two of the four read stops.
Give a `files:` hint the module the list lives in, not only its consumers — here `inventory.rs` was
the real first file. Keep the gate runs in one stop per iteration: three `ci` runs after one `fmt`
failure is a habit, not a measurement.
