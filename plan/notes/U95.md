# U95 — Two skills carry the interface rules to where they are needed: placing a capabil

Two skills carry the interface rules to where they are needed: placing a capability and designing an operation.

## What was measured

- `AGENTS.md` §1.3 named one skill, and `xtask/src/skills.rs` required exactly that one
  (`DESIGN_SKILL`). A second or third interface skill could be added and never routed, or dropped
  from §1.3, and the gate stayed green: the routing rule was a sentence in one file, not a list.
- The place of a capability already lives in `crates/ui/src/inventory.rs` (`Row`, `Place`, `Applies`,
  `ActsOn`, `ATOMS`), but no skill taught it: the rule reached a session only through ADR 0117, after
  the button was already written. The same held for the atom question (ADR 0118).
- `references/surfaces.md` read as the catalogue of *where things are offered*, which invited a
  second list next to the inventory; the checklist had no line about the inventory, atoms or icons.
- The operation lifecycle (arm, preview, typed number, commit, cancel, undo) was described only in
  ADRs and in the code (`apps/furnicraft/src/document.rs` `handle_keys`, `Session::set_preview…`,
  `crates/ui/src/command_bar.rs`), never as one procedure.

## Decisions

- Two skills, because the two triggers happen at different moments: `place-capability` runs when an
  id or a place is added, renamed or removed; `design-operation` runs when a gesture or a mode
  appears. Folding either into `ui-design` would load it on every `crates/ui` change and bury the
  decision that must be made first.
- `ui-design` keeps the brief, the invariants and the rubric, gains a short "Two procedures this one
  calls" section and points at both. The checklist gains a `G. Placement` section (22–24) instead of
  renumbering A–F, so an existing verdict (`A1`, `C10`) keeps its number.
- `surfaces.md` states what it is not: it owns surfaces and their files, the inventory owns the places
  and the actions.
- `xtask/src/skills.rs` holds `ROUTED_SKILLS` (the design skill and the two it calls) and
  `check_router` fails once per missing name, so §1.3 is a checked list rather than one path.
  `plan/map.md`'s "Skills and prompts" row says so.

## Ruled out

- A behavioural lint over gestures (every state answers Escape, one undo entry per operation): it
  cannot be read from source text without a model of the state machine, and a half-check would let a
  session believe the gate proved the operation. The procedure plus the review form is the honest
  instrument.
- A row per skill in `plan/map.md`: that row already owns the whole `.pi/skills` tree and the gate,
  and a second index would drift from the folder.
- A new `Place` variant or a second surface list in a skill: ADR 0117 fixes the list, and a skill that
  copies it would become a third register.
