# J2 — the schema a caller reads is the one the parser enforces

## What was measured

- `crates/engine/src/commands.rs` defines 57 `CommandSpec`s, each with an id, a `Message` label,
  an `enabled` predicate and a `run`; the parameter struct is named nowhere in the spec, only inside
  each command's own `parse`. `z3l commands --json` printed `id`, `label`, `creates` and nothing
  else (ADR 0183).
- The 57 parameter structs name 20 types of `model` and 2 of `units`. Six of those model types are
  written in a wire form (`#[serde(try_from = "…Wire")]`): `Contour`, `Path`, `PanelNominalSize`,
  `PanelRect`, `Placement`, `Envelope`. `schemars` describes such a type **through its wire form**,
  which is what the parser accepts — the happy accident that made the schema true rather than
  plausible.
- `schemars` 1.2.3 and its three dependencies (`dyn-clone`, `ref-cast`, `schemars_derive`) were in
  the local registry cache; nothing was fetched. It is a derive over `serde` types with no build
  script and no C sources.
- The report of all 57 commands with their schemas is 226 KiB of pretty JSON; the doc comments of
  the types arrive as `description` strings.
- `#[serde(default)]` reaches the schema: `panel.create` requires exactly `parent`, `name`,
  `nominal_size`, `material`, `placement` and lists `class`, `outline`, `bevels` as optional, which
  is the parser's own reading of the same attributes.

## Decisions

- `CommandSpec::new::<P>` takes the parameter type; `id` and `label` stay arguments. A `Copy` const
  spec can hold a monomorphised `fn() -> Value`, which is why the schema is a function and costs a
  dispatch nothing.
- The trait-free turbofish, not a `CommandParams` trait carrying the id, the label and a parse: it
  is one edit per spec instead of an `impl` block per struct, and the drift it would close (a spec
  naming one struct while its `run` parses another) is a review question either way. The fuller
  shape — the spec parses and hands its `run` a typed `&P` — is a task of its own.
- The derives live beside the types (`units`, `model`), recorded in ADR 0194; a
  `#[schemars(with = "i64")]` per field would have been a hand claim nothing checks.
- The wire types of `try_from` structs derive too, because the schema of a `Contour` a caller sends
  is the wire form. Their `JsonSchema` has no other consumer and is not dead code: it is reached
  through the outer type.
- Three tests in `crates/engine` and three in `app/src/cli/commands.rs`: every spec publishes an
  object schema with `additionalProperties: false` and `required ⊆ properties`; `panel.create`'s
  optional trio stays optional; a nested model type is described through its own definition; and the
  report's rows carry the same schema the spec prints.

## Ruled out

- **The `enabled` reason on the same surface** (the entry's Shape). `enabled` is a `bool` over 57
  predicates that run per frame; a sentence means a second return type, a sentence per conjunct and
  57 rewrites, and the door that needs it (ADR 0185's tool list with `enabled` *and* params) arrives
  with J3/J5. Left for that task; the schema does not depend on it.
- **Reading the field names out of serde's `missing field` message** to cross-check the schema, the
  reflection trick J1 already refused: it answers the first field of an empty object and stops at
  the first type error.
- **A hand-written field table** beside the registry (ADR 0185 refuses it) and a `with = "…"`
  override per field.
- **A golden file of the whole report.** It would fail on every doc-comment edit and say nothing
  about whether the schema matches the parser.
- **Printing the schema in the text form.** `z3l commands` is for a person scanning ids; a hundred
  lines of JSON per command on a terminal is noise.
