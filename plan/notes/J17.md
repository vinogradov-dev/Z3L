# J17 — the product a caller works in, and where opening lives

## What was measured

- `Session::open_product(id) -> bool` (`crates/engine/src/session.rs`) was the only door: the window
  opens what a person double-clicks, the headless CLI opens with `--product`
  (`app/src/cli/recipe.rs::open_product`, called before the batch by `perform` and `served::open`),
  and nothing on the tool surface could open anything. Measured over the channel: `product.create`
  succeeded and `command_list` answered `open_product: null`, so `panel.create` stayed
  `enabled: false` and `query niche` refused — every furniture command unreachable after the frame.
- The tool surface already reported the open product on `command_list` (`listing` in
  `crates/mcp/src/server.rs` prints `open_product`), but a batch report had no such field, so a
  caller could not learn what it ran in.
- Both agent doors share one dispatch: `mcp::dispatch(&mut Session, &BatchRequest, Door)` is what
  the stdio server, the window channel (`app::answer_channel`) and `mcp serve --attach` call, so a
  field added there is one field on every door.
- `BatchRequest` was `{steps, atomic, dry_run}` and `RunRequest` `{command, params, dry_run}`; the
  run is a batch of one step (`RunRequest::batch`), so one field covers both.
- The CLI's own sentence for a bad `--product` (`no product has id …; --product names a product of
  the scene`) lived in `recipe.rs` and had no test, and the tool surface had no equivalent at all.

## Decisions

- **A field on the batch, not a second tool.** A `product` on `command_run` and `command_batch` is
  one call and one answer; a tool that only opens would be a write hidden in `query` or a fifth
  coarse tool whose only purpose is to set state the next call needs (ADR 0212).
- **Opening happens before the steps and is not one of them.** It moves no revision and leaves no
  undo entry, so a caller that opens a product and whose steps then refuse keeps the product open
  and loses the change — the two acts have two costs, and the batch only owns the second.
- **The refusal is one sentence, and it is the engine's.** `OpenProductError` says
  `no product has id {id}; name a product of the scene`, the CLI fails the run with it and the wire
  answers the call refused with it; the open itself stays `Session::open_product`, which is what the
  double click calls.
- **The answer names `open_product`,** read from the session after the batch — the same field
  `command_list` prints, so a caller that named none learns which product the person had open
  instead of assuming.
- **Plan mode does not stop the open.** ADR 0190 makes the mode a switch over what may write the
  document; this writes no document state, and a plan of a product is only a plan of the product the
  caller named.
- **The command line keeps its own flag and its own order.** Opening before the batch is what
  `--product` already did; it now goes through `open_named_product`, so the sentence is shared. A
  recipe that *creates* the frame it builds in still needs the frame opened after its first step,
  which is X112 (create leaves the product open) and J18 (a step naming an id an earlier step made).

## Ruled out

- **A `session.open_product` tool.** A fifth coarse tool that writes view state, for a value every
  batch already needs; the `product` field is the same act with no round trip.
- **Opening as the first step of the batch.** A batch is one undo entry and rollback is all or
  nothing, so opening would be taken back with the refusal — and it would put a view operation into
  a list of document commands, where every other entry mutates and is undone.
- **Guessing the product when the scene holds one.** Opening a lone product without being asked
  hides a caller's mistake (it may be working in another one on purpose); the CLI's rule is the
  exception a person's flag-less run gets, not the wire's.
- **Naming the product by path or name.** A caller that just created a product reads its id from the
  answer; a name would make the lookup a second registry and break on rename.

## What the tests pin

- `crates/mcp/tests/served.rs::a_batch_names_the_product_it_works_in` — a batch names the second of
  two products, the panel lands inside it, the answer says `open_product`, undo takes back the panel
  and not the product, and an id that is not a product refuses before anything dispatches.
- `…::a_scene_with_two_products_and_none_named_refuses_in_the_commands_words` — no product named is
  no guess: `rolled_back`, `open_product: null`, and the command's own
  `cannot create furniture here: Create a product first.`
- `…::naming_a_product_opens_it_with_no_revision_and_no_undo_entry` — the steps refuse, the revision
  is where it was, `can_undo()` is false, and the product is open.
- `crates/engine/src/session.rs::a_named_product_opens_or_names_the_id_that_is_not_one` and
  `app/src/cli/recipe.rs::an_id_that_is_not_a_product_is_refused_in_one_sentence` hold the engine
  rule and the flag's half of it.
