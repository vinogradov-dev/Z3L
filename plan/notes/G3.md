# G3 — What was measured

## What was measured

- `crates/geom/src/boolean.rs` already owns the exact overlay of ADR 0043: `union_regions`,
  `intersect_regions`, `subtract_regions`, each `&[Region] -> Vec<Region>`. A result is zero or more
  `Region`s and every one of them may carry hole rings. Nothing converts a `Region` back to a
  contour or a path; `Region::outer()` and `Region::holes()` are the only pieces.
- No engine command id carries a boolean. `sketch.booleans.{union,subtract,intersect}` and
  `model.booleans.*` exist only as `planned()` cells (`crates/ui/src/toolbars/spec.rs:648-650`,
  `:805-807`) with `icon: None`, while the artwork is
  `icons::contour::BOOLEAN_{UNION,SUBTRACT,INTERSECT}` (`assets/icons/contour/boolean-*.svg`) and the
  labels are `Message::ToolUnion`, `ToolSubtract`, `ToolIntersect`.
- Both doors the entry names take exactly one ring. `object.contour.replace` takes a `model::Path`
  (one open or closed chain; `Path::to_contour` refuses an open chain and a self-crossing ring with
  `PathError`), `panel.outline.set` one `model::Contour` behind `validate_panel_outline`, which
  rejects anything that is not one valid ring.
- A hole is representable only as a panel's machining record
  (`MachiningParams::Cutout(CutoutShape::Contour(_))`, door `panel.machining.add`,
  `crates/engine/src/panel_cmds/machining.rs`). The material of a panel is
  `PanelGeometry::core_region()` = outline minus through cutouts, a `Region` with holes
  (`crates/param/src/machining.rs:159`), so a boolean hole on a panel maps to a cutout, not to the
  outline.
- Geometry is per node and local: `crates/mesh/src/lib.rs:760` evaluates `Geometry::Path` into one
  `NodeGeometry::polyline` (a single point sequence, `polyline: Option<Arc<[DVec3]>>`). Several
  rings, drawn filled, have no field there today.
- A live step that names a cutter makes a result depend on another node's placement. The precedent
  for that dependency is a panel's derived holes, cached with `HoleInputs` (placement + objects,
  O10/ADR 0150) rather than by the payload alone.
- The overlay previews one `model::Geometry` per node (`crates/engine/src/preview.rs`), with a
  version and no revision. It can show a path today because a path evaluates to a polyline.
- Selection is shell state (the editor's `selected_nodes()`); no command takes two node ids yet —
  the nearest is `object.path.extrude` (`object` + `height`).
- Existing conversions: `model::Contour::to_geometry()` → `geom::Contour`; the reverse is built
  segment by segment (`ContourSegment::from_geom`), as `crates/ui/src/contour_edit.rs` does on apply.

## Decisions

- Opening question for the owner, D1 (storage of a tool-mode step): a new payload
  `Geometry::Sketch { base: Path, steps: Vec<BooleanStep> }` rather than a feature list inside
  `Path`. `Path` is the drawing primitive every command, the contour editor and the mesh read; a
  payload with a history is the shape `Constructive` already has for solids, so the step reuses one
  pattern instead of widening the one every rule touches.
- Opening question for the owner, D2 (what a multi-ring result does): the first slice refuses a
  result that is empty, several rings or carries a hole, with a sentence that names which; the
  ring-set payload (and a panel hole as a cutout record) then arrives with tool mode, which needs
  the payload anyway. The alternative is to introduce the payload now, which also gives the preview
  a filled region to draw.
- D3: the one-shot command writes both ends in one revision and one undo entry: the target through
  its existing door and the source through `Project::remove_nodes`. The target is the last selected
  ring, the cutter the other one.
- D4: both rings are read into world millimetres through `Project::world_placement`, the boolean runs
  there, and the result is brought back into the target's local frame before the door sees it. A
  live step cannot work that way — it must re-derive on the cutter's placement, which only a cached
  payload can do.
- D5: with two rings selected the cell computes the result and sets it on the overlay; ✓ dispatches
  the one command and ✕ drops the overlay. There is no number to type, so the card shows the
  operation (and, once D1 lands, the mode).

## Ruled out

- Writing the result into the document per frame: ADR 0093 already closed that road for the
  extrusion pull.
- Widening `Contour` to carry holes: it is the ring every banding, bevel, machining and outline rule
  reads, so a second ring list inside it would turn one invariant into two.
- Making a boolean hole a machining record from the one-shot command: it becomes a record with its
  own id and offsets, so undoing the boolean could not restore the outline and the cutout as one
  edit. It is a separate door with its own command and its own entry.
- Taking `sketch.booleans` for the three commands while `model.booleans.*` also exists: the entry
  names `contour.boolean.*`; the third group's ids are settled when a 3D boolean exists.
## The owner's rule (2026-11-20)

- A contour boolean creates a **new object**; it does not rewrite one of the operands. The new
  object may hold several contours, and then it is a drawing of several contours — the area/hole
  representation is a later idea (SketchUp: hover a push/pull on the region between contours, see it
  highlight, click to extrude), filed as its own entry.
- An operation takes one *base* contour and any number of further operands; the base is the first
  one selected. Sources are consumed by the operation except those marked **`инструмент`** — a flag
  on the object. A tool object stays in the tree and its shape never enters the created object: it
  is a kept stamp, not a live operand, and clearing the flag makes it one-shot again.
- A panel outline is never an operand of a manual boolean, before or after creation. A panel's
  cutouts are a panel parameter, and a cutout that splits the panel into more than one piece is an
  error the operation refuses rather than a panel that stops drawing.
- A subtract whose contours never cross (a cutter wholly inside the base) creates nothing, because
  what it would leave is a hole and a hole is an area.

## What this closes

- D1 is answered without a step: no boolean is stored on an object, so no payload with a feature
  history is added for it.
- D2 is answered: several rings are a normal result, and a hole is not.
## What landed

- `geom::Contour::placed(turn, mirrored, offset)` is the rigid flat transform one drawing frame
  costs against another: lines stay lines, arcs keep their radius and reverse their sweep under a
  mirror, and the result is exact.
- `model`: `Geometry::Contours` (`Contours`, validated closed rings, one line chain per ring) and
  the object's `tool` flag; schema 29; the golden carries a two-ring drawing and one tool mark.
- `engine::contour_cmds`: the three commands, `ContourBoolean`'s parameters, `ContourOp`,
  `ContourBooleanPlan` (the calculation without the write) and `BooleanError`'s sentences.
- `ui`: the three ribbon cells are live with the contour theme's artwork, the editor owns the arm
  (`editor/boolean.rs`), and the shell draws its card, its overlay and its Enter/Escape/✓.
- The panel-cutout rule the owner stated is N30: a cutout that splits a board is refused by the
  command, which today accepts it and stops drawing.

## What was ruled out on the way

- A live cutter (a stored boolean step) — the owner's rule replaced it with the `tool` mark, so no
  payload with a feature history was added.
- `panel.outline.set` as a boolean door: a panel's outline is one ring and its cutouts are its
  parameters, so a panel is never an operand.
- A self-crossing operand as a test case: `Path::new` refuses to store one, so the refusal lives at
  the drawing rather than at the boolean and cannot be reached from the document.
## Follow-ups the owner found by using it (2026-11-20)

- X98: a body's profile is not a legal operand. The extrude cell turns a drawing into a
  `Constructive` in place, so the maker's habit — draw, extrude, cut — ends in "not a drawn
  contour". `/home/alx/scene.z3l` is that scene: two extruded bodies, both refused.
- X99: the armed boolean does not show which ring is the base; the highlight moves to the operand.
- X100: a contour set cannot be extruded, so an intersection of three rings is a dead end.
- X101: opening an older scene answers a field error instead of the schema sentence, because the
  schema check runs after the tree is parsed.
- The card's ✕ fell through to the extrusion's cancel and left the mode armed: fixed in `6aba8cb`.
## The owner's scene, and the joint rule it broke (2026-11-20)

- `/home/alx/Documents/scene.z3l` holds two circles and a board, all drawn paths, schema 29. The
  intersection of the 650.308 mm circle at (90, −40) with the 730 × 810 board at (155, 645) was
  refused with `path segment 2 does not meet the next segment`.
- Measured: the geometry ring's own joints are 1e-13 mm wide, so the gap appears at the document
  boundary — converting the arc to whole micrometres and millidegrees. The stored joints were 4.2
  and 7.7 µm wide, and the rule allowed `1 µm + radius × 8.73e-6` = 6.7 µm for a 650 mm radius.
- Root cause: an arc's endpoint depends on the *sum* of two rounded angles (start and sweep), so its
  rounding is a whole millidegree, twice what `arc_slack_micrometres` counted. The base is also two
  units, not one: two independently rounded points miss each other by at most 1.42 µm.
- Fixed in `7e0b0ce`: the slack is `2 + radius × 1.746e-5`, the base is 2 µm, ADR 0072 carries the
  corrected formula, and the owner's own circle-versus-board is the regression test.
- `z3l run` on the owner's file now creates the ring and consumes both sources.
- The two bodies in `/home/alx/scene.z3l` are still refused as operands: they are constructive
  payloads, which is X98.
