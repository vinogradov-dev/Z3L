# J18 — a batch step names what it made, and a later step refers to it

## What was measured

- `crates/engine/src/batch.rs` held `BatchStep { command, params }`: a command id and the JSON its
  own parser takes. `CommandOutcome` already answered `created_id()` and `created_machining_id()`,
  so the id a step needs was known the moment the step ran and nowhere before it.
- `Session::batch_in_scope` runs `batch::run` on a trial copy and installs it only when the effect
  landed, so a resolved reference can never leak into the real document on a refused batch.
- `batch::run` broke the loop at the first refusal, so a step after a refusal never runs: a
  reference to a step that refused is unreachable, and the case worth guarding is a name no earlier
  step gave.
- `BatchReport`'s `created`/`changed` lists come from diffing the two documents, so a panel created
  and banded in one batch is reported as *created*, never as changed — the panel is not in the
  before-document at all. A test that asserted `changed` first read a hole in the assertion, not in
  the report.
- The three doors each built a `BatchStep` from their own line: the CLI recipe
  (`app/src/cli/recipe.rs`), the tool server (`crates/mcp/src/server.rs`) and a chat turn. The
  recipe's line parser refused any key but `command`/`params`.
- The wardrobe recipe (`app/tests/recipes/wardrobe-800x460x2200.jsonl`) writes the ids of one fixed
  scene into 19 banding lines (`3`…`16`), which is the workaround the task names.

## Decisions

- **`as` names, `$ref` refers.** A step carries an optional name (`BatchStep::named`, `"as"` on the
  wire), and a parameter object that holds `$ref` and nothing else is replaced by the id a named
  step created. `as` because a step's own `params` already carry a `name`, and two `name`s in one
  line read as one.
- **`$ref` is a reserved shape inside a step's parameters.** An object with `$ref` is a reference or
  a mistake — a non-string value, a blank name or a second key is a refusal. The alternative, "only
  an object that looks exactly like `{"$ref": "<known name>"}` is a reference", would hand a typo to
  the command, which would answer `invalid type: map, expected a nonzero u64` and name no step.
- **Resolution lives in `batch.rs` and runs before `dispatch_in`**, on the parameters the report
  echoes back unchanged: the command, its door and its test never learn the concept (ADR 0214).
- **The walk runs even when no step has named anything.** The first version skipped it while the
  name map was empty, which is exactly the state in which a reference cannot resolve — the raw map
  reached the command and the sentence named no step. Cost: one shallow walk per step.
- **A refusal is the command's own `InvalidParams`**, so the door, the CLI's exit code and the
  report's `refusal` field needed no new variant and no new arm: `invalid parameters for
  `panel.edge_banding.set`: `frame` is step 1's name, and step 1 created no node`.
- **A name is claimed before the command runs**, so a second step taking a name is refused instead
  of silently shadowing the first; what the step made is recorded after it ran.
- **`StepRequest` grew `StepRequest::new`**, so the three call sites that built the structure by hand
  read as one line each and the next field costs them nothing.
- **The report echoes the reference as the caller wrote it** and adds the step's `as`, rather than
  echoing the resolved id: the row of the step that created the node already carries `created`, so
  the mapping is in the answer and the echo stays what the caller sent.

## Ruled out

- **Using `CommandOutcome::created_machining_id` for the name.** A machining id shares the id space
  and would resolve as a number, but a name that can mean two kinds of record is a name whose
  mistake is silent (a cutout id where a panel id belongs). The node is what the Shape asks for; a
  command that must address a machining record is a later decision.
- **Resolving in each door.** The CLI, the tool server and a chat turn would then have three copies
  of one rule, and the third would drift (ADR 0185, ADR 0190).
- **A reference that names a step by number** (`{"$step": 3}`): a line inserted in the middle of a
  recipe would silently re-point every reference after it.
- **Keeping the ids in the wardrobe recipe**: with a name per creating step the recipe no longer
  depends on the scene's counter, so the fixture stops being a fixture with hard-coded ids.
- **A new `CommandError` variant** for the batch: a reference that cannot be resolved is a parameter
  set the command cannot use, and `InvalidParams` already carries the command's id.
