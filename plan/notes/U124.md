# U124 — the overlay front panel, and where its lap lives

what a session measured about the mounting, the lap and the two places a factory number can sit

## What was measured (2026-11-24)

- The fill is one plan and one command over it. `FillRequest` (`crates/model/src/project/fill.rs:73`)
  carries `point`, `fill`, `mode`, `thickness` and `free`; `Project::fill_plan_in` (`fill.rs:239`)
  turns it into a `FillPlan` — outline, nominal size, placement, bevels, the two free ends and the two
  polygons — and `board()` (`fill.rs:420`) is the whole placement rule.
- The wall is `Fill::WidthAndHeight`: `stance()` (`fill.rs:346`) puts the board's local `X` on the
  product's `Z` (the niche's height), `Y` on `X` (its width) and the material on `Y` (the depth),
  `t = 1`, no `against` flag. `board()` takes the free place from
  `niche.local_min[t] .. niche.local_max()[t] - gap` (`fill.rs:426`) and writes
  `translation[t] = stance.face(value, gap)`, which for this stance is `value` itself. So the board
  fills the opening: its inner face is the niche's start plane, and that is the inset reading today.
- A clip already exists. `trim_footprint` (`fill.rs:1282`) cuts a convex footprint by the half-planes
  of the body boxes the sight switched off (`hidden_boxes`, `fill.rs:1234`, from
  `body_surfaces`, `niche.rs:920`), keeping the side the measured point stands on and the larger
  side where the point is inside the body. An axis-aligned half-plane keeps a rectangle a rectangle,
  which is why one rule serves both a ring and a box.
- A ring can be offset per edge: `set_back` (`fill.rs:832`) moves every edge's line by its own
  distance and intersects the neighbours. It refuses a negative distance, so it is the inward half of
  what a lap needs; the same math grows a ring outward.
- The click does not run `panel.fill`: `create_fill` (`app/src/document.rs:2498`) dispatches
  `panel.create` through `Editor::create_panel_sized` with the ghost's own outline, bevels and
  placement, so a mounting has to travel on `PanelCreate` (`crates/engine/src/panel_cmds/panel.rs:47`)
  — `panel.fill` stays the caller's door and takes the same value (N37).
- The card already draws named option rows (`ToolChoice`, `crates/ui/src/tool_card.rs:126`, U123): the
  fill's two rows are built by `Document::fill_choices` (`app/src/document.rs:1916`) and a pick is
  mapped back by `fill_choice`. A third row costs one entry in each.
- The panel stores its data through `Panel` (`crates/model/src/panel/mod.rs:120`, `PanelWire` at 913),
  so a mounting record is one field, one setter, one wire field and one validated setter in
  `project/panel_cmds.rs`.
- `build_plan` (`panel.rs:714`) already re-plans an existing part: it removes the part from a copy,
  measures the niche at the part's centre and plans the other build. It hands `FillRequest` no mount,
  so an overlay part re-cut today would come back inset.
- Scene settings have no home yet: `SceneFile` (`crates/project/src/lib.rs`) has `document` and the
  preserved `extra` only, `docs/domain/scene-file.md` §3 names "scene settings: world ambient and,
  later, render settings" and no field carries one. `app/src/settings_store.rs` is the *workspace*
  file (theme, language), which is what the task rules out for the lap.
- An envelope key is additive: `extra` preserves every top-level key this build does not know
  (`crates/project/src/lib.rs` §Loading, `Envelope`), so a `settings` object neither breaks an older
  build nor needs `format_version` to move.

## The shape I would build

1. `model`: `MountForm { Inset, Overlay }` and `PanelMount { form, laps: [Length; 4] }`, the laps in
   the panel's own edge order (edge 1 bottom, 2 right, 3 top, 4 left, the numbering `EdgeId` already
   uses). `FillRequest` gains `mount: Option<PanelMount>`; `None` is the inset board and today's plan
   to the micrometre. `FillPlan` answers the record it made, with the laps **achieved** after a clip.
2. Overlay in `board()`: the frontal section's box grown by the four laps, cut back by
   `trim_footprint` against the bodies standing in front of the opening plane, placed one thickness
   off `niche.local_min[t]` on the far side of the void, so the inner face is the start plane. The
   grown box stays a rectangle through an axis-aligned clip, which is what keeps four laps meaningful.
3. `panel.create` and `panel.fill` gain `mount`; `create_panel` writes it in the same revision and the
   same undo entry. The eight engine tests that build `PanelCreate` keep working with `None`.
4. The fill's card gains a third row (inset/overlay) carried by `PanelBuild`/`FillArm` as view state,
   offered for the frontal class only.
5. `project`: `SceneSettings { lap: Length }` (14 mm default) as the envelope's `settings` key, read
   with `#[serde(default)]`, written unchanged, `SceneFile::settings()/with_settings()`; the shell
   seeds the fill's laps from it.
6. `ui/panel_card.rs`: a mounting row (inset/overlay) and four lap fields, one per outline edge,
   through one new command `panel.mount.set`.
7. ADR: the lap is document data, the default is the scene's, the factory's numbers' home is O2's
   standards file; `plan/debt.md` records the flip from the 14 mm fallback to that file.

## The one question for the owner

What does a lap typed into the panel card do to the board it describes?

- **My default — it re-lays the board.** The card's number is the lap the owner wants; the command
  measures the void again (the part's inner-face centre is already outside the void, so the point has
  to step one micrometre in), plans the board with the new laps, re-clips it and writes the size, the
  placement and the achieved laps as one undo entry — `build_plan`'s own path with a mount. The
  record and the board cannot disagree.
- **The smaller reading — it only stores the number.** The card edits the record, the board stays
  where the creation put it, and the number is read by the rules that need a mounting (the door gap,
  the hinge; `plan/questions.md` line 70). One command, no model work, but a record that says 20 while
  the board was cut at 14.

## Ruled out

- A second measurement of the void in the shell: the niche atom is the one reader (ADR 0118).
- A lap on the tool card: the owner said the lap is one default out of the project's settings, and a
  number beside the class would be a second source for the same value.
- An overlay post or shelf: only the frontal board stands across the void's front, so the model
  refuses `Overlay` for a pair whose stance is not the wall's, with a sentence.
- Growing a contour ring by a lap: the niche's frontal section is a polygon, so the grown board is a
  polygon and a four-edged one whenever the clip is axis-aligned. A ring keeps a curl the four laps
  cannot describe.
## What the owner ruled (2026-11-24), and what landed

- **The trim is a panel parameter, not a mounting form.** «Подрезка торца»: one signed number per
  end, positive cutting in, negative letting the board out; the size follows the number. It does not
  accumulate: setting a number moves the end by the difference from the stored one, so typing the
  same number twice moves nothing and the first one puts the end back. `PanelTrims` stores the four
  in outline-edge order; `panel.trim.set` is the person's door and `trimmed_frame` is the arithmetic,
  including the origin that follows an end at the panel's own zero corner.
- **There is no form to store.** A mounting is an operation. The two states are told apart by the
  placement along the depth and by the trims, so the inset-to-overlay operation the owner described
  is not in this task; `plan/debt.md` records that it is missing, and that it would also rewrite the
  hinge model once hinges exist.
- **At creation the lap is the frame's answer, inside the settings' cap, per end.** A part that
  reaches the opening's plane from behind gives that end a face to run over — the nearest one, from
  the opening's edge out — and no part there is no lap. A part standing proud of the plane stops the
  end at its near face (which trims the board *inside* the opening when a neighbour reaches over it),
  and a part proud of the face inside the opening is a refusal with a sentence. `overlay_rect` settles
  the four ends against each other in passes, so a neighbour at one end never bites into another.
- **Only the frontal pair takes a mounting**, and the model says so by name (`NotFrontal`); the fill's
  card asks the mounting row only for the wall.
- **The lap's default is the scene's.** The envelope's `settings` section carries `overlay_lap`
  (14 mm, `DEFAULT_OVERLAY_LAP`), `SceneFile::settings()` answers the default for a file without the
  section, and `SceneWriter` gives the number back on every save. The key is additive and preserved
  by a build that does not know it, so `format_version` stays 1 and only the golden gained the key.

## What was measured, and how it was checked

- Headless: `an_overlay_front_runs_a_lap_past_the_opening_and_lies_on_its_face` (628 × 748 over a
  600 × 720 opening, trims −14 each, inner face on the start plane), `an_end_with_no_part_behind_it_
  takes_no_lap`, `a_part_standing_in_front_stops_the_lap_at_its_own_edge` (+22 on the stopped end),
  `only_a_front_takes_a_mounting_and_an_inset_board_is_untouched`, the engine's overlay click, the
  overlay part re-cut by `panel.build.set`, `panel.trim.set` in both layers, the card's four rows and
  the ring's sentence, and the shell's `an_overlay_click_is_one_front_one_create_and_one_undo`.
- The inset path is untouched: `PanelTrims::ZERO` skips the field in the file, so the golden and every
  fixture written before this task round-trip byte for byte, and every existing fill test passes
  unchanged.

## What this does not do

- No operation turns a laid front into an inset one (owner's description, later task).
- The lap is capped per end and clipped per end; a shaped (splayed) void still gets a rectangle,
  because a facade is one and the four numbers are the whole vocabulary of the record.
- A trim is a number on the end, not a distance from the opening: a hand resize of the same side
  leaves the number alone (`plan/debt.md`).
## Correction, the owner (2026-11-24): a parameter never moves the origin

This supersedes the paragraph above that made the placement follow a trim. The rule: **a command that
changes a panel's geometry through its parameters does not change the origin**, because the origin is
how a person controls where the part is. So the trim is read where the outline is generated — the
material sits inside the frame at a cut end and outside it at a let-out end — and
`panel.trim.set` writes neither the nominal size nor the placement. An overlay front's frame is the
opening, so its corner is where the part is placed and the resolved rows report the material
(628 × 748 over a 600 × 720 frame). `panel.build.set` reads which board a part is from where it
stands, so a trimmed shelf inside a case is not re-planned as a front, and the ghost's callouts measure
the board's own polygon (ADR 0240).
