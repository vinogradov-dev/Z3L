# J10 — a preview of the scene, drawn by the shell and handed to the tool server

## What was measured

- `crates/render/src/lib.rs` `RenderTargets::new` adds `COPY_SRC` to the colour texture only under
  `cfg!(test)` ("the product never copies its colour target"), so a release build could not read the
  picture back; the texture is `Rgba8Unorm` and the shader already writes gamma-corrected values.
- `crates/final/src/image.rs` `encode_png(&Image, exposure)` takes *radiance* (`f32` linear) and runs
  the ACES curve and the sRGB transfer function over it, so the tracer's encoder cannot take the
  viewport's already-display-ready bytes. `png` is already in the tree through `final` and `epaint`.
- `crates/mcp/src/server.rs` answers every tool through a free function over `&Session`
  (`listing`, `findings`, `asking`, `dispatch`); `mcp` is forbidden `egui`, `wgpu` and `eframe`
  (ADR 0186) and holds no device.
- `crates/mcp/src/tools.rs` `Answer` is a JSON body plus a `failed` flag, and `server.rs` `result()`
  turns it into one text block; `rmcp` 3.11 carries `ContentBlock::image(data, mime)`.
- `crates/mcp/src/channel.rs` `Call` has five variants and no preview; a window answers at a frame
  boundary (ADR 0187, ADR 0223).
- `app/src/ui_shots.rs` `render_state()` builds a device with no window and is production code
  (`mod ui_shots;` in `app/src/main.rs` is not test-gated), so a headless preview needs no new way to
  reach a device.
- `app/src/scene_build.rs` `evaluate(cache, kernel, session, flags, open_product)` returns
  `EvaluatedScene { frame, bounds, .. }`, and `home_camera(bounds)` + `scene_camera(project, view)`
  are the framing the shell already uses for *Frame all*.
- `engine::Session` holds no camera: viewport navigation is the shell's (ADR 0029). A headless
  process therefore has no view to copy, and "what the person sees" cannot be the preview's rule.

## Decisions

- The port lives in `mcp` (`Previewer`: `Debug + Send + Sync`, takes `&Session` and a `PreviewSize`,
  answers PNG bytes — the shape `SceneSink` already has) and the implementation lives in the shell
  (`app/src/preview.rs`): evaluate, fit, `ViewportRenderer::render`, `read_color`, `encode_rgba8`.
  The server holds `Option<Arc<dyn Previewer>>`; `None` is a process without a device, and the tool
  refuses with that sentence instead of a protocol error.
- The picture travels as an MCP image block, not as base64 inside the JSON: `Answer` gains an
  optional image, `result()` appends `ContentBlock::image("image/png")`, and a client draws it
  without decoding our answer.
- Two caps, both refused and never quietly clamped: `MIN_SIDE = 64`, `MAX_SIDE = 1600` per side,
  checked before anything is drawn; `MAX_BYTES = 4 MiB`, checked after encoding. A size the request
  is over is a refusal that names the bound, so a caller learns the shape it may ask for.
- base64 is twenty lines in `mcp` with a test: a dependency for one table is what AGENTS §4.8
  rules out, and `rmcp` wants the string, not the bytes.
- `final::image` gains `encode_rgba8(width, height, &[u8])`, and `encode_png` becomes its caller:
  the tree keeps one PNG writer, so the preview and the final render cannot drift apart.
- `render`'s colour target always carries `COPY_SRC` and gains `read_color(device, queue)`: the
  256-byte row alignment is the business of the crate that knows the format.
- The framing is the document's own: an authored camera wins, otherwise the view is fitted to the
  scene (`home_camera`). A window and a headless process therefore draw the same picture, which is
  what makes the test's "the golden scene at two sizes" meaningful.
- ADR 0228 records the port, the image block and the two caps.

## Ruled out

- A `wgpu` device or context in `mcp`: ADR 0186 forbids the dependency, and the whole point of the
  task is that the client needs no device.
- Raw RGBA or a base64 string in the JSON body: 1600 x 1600 is 10 MB before base64, and no client
  draws a `body` field.
- Reusing the tracer: a converged final render is seconds per image and it is not the viewport's look.
- Copying the window's camera in a headless process: there is no camera in `Session` to copy.
- Clamping an over-size request down to the cap: a call that asked 4000 x 3000 would receive a
  picture it did not ask for, and a test could not tell a clamp from a refusal.
