# K3 — the order package comes from a command line, not from a window

## What was measured

- `main.rs` had no argument handling at all: `fn main` built `NativeOptions` and called
  `eframe::run_native`, so the only way to reach `furnicraft-export` was a Rust caller.
- `crates/export` is a library with no window, no GPU and no file dialog (K2), and the intended
  entry points already exist: `OrderPackage::build`, `write_dir`, `write_single`, `now_timestamp`.
- The scene file carries the document and nothing else, so a headless run has no catalogue:
  `apps/furnicraft/src/scene_build.rs` (`default_catalog`) is the catalogue a new session starts
  from, and its ids (1, 2, 101, 102) match the ids `furnicraft-testkit::sample_catalog` uses, so a
  fixture written with testkit resolves in the default catalogue.
- `ExportOptions` already has every field the CLI needs: `timestamp: Option<String>` (the manifest's
  `exported_at`), `DocumentMeta { file, revision, hash }` and `order`. Nothing had to grow.
- `crates/project/tests/golden/scene.fcs` is a real saved scene, and it exports as eleven tables
  (`nodes` 9, `parts` 2, `contours` 8, `banding` 1, `machining` 1, `materials` 1, the rest 0).

## Decisions

- One new module, `apps/furnicraft/src/cli.rs`, in the binary that already owns the composition
  root: no second binary and no new dependency (`std::env::args`, `std::process::exit`). It parses
  to a `Command` value, exports, and returns the lines to print, so the test drives the whole job.
- The subcommand is handled in `main` before `run_window`, so no surface is ever created; the
  `Window` variant is the fallthrough, which is what a double click sends.
- `--out` names a directory for `bundle` and a file for `single`: the two writers take exactly those
  two shapes (`write_dir`, `write_single`), and a second `--file` flag would be a second way to say
  the same thing.
- `DocumentMeta.file` is the scene's file name and `revision` the document's own revision, so a
  reader can tie a package to the file it came from. `hash` stays `None`: no hash is computed
  anywhere in the tree, and a guessed one would be worse than an absent field.
- `order` stays `None`: an order number and its revision are the workshop's data, and the entry for
  this task does not place them on the command line. The manifest omits an empty order block.
- Exit codes: 0 for a written package or printed help, 1 for a failed export (bad scene, bad path),
  2 for a usage error. The sentence goes to stderr as `furnicraft: <message>`.
- The printed report is one line per table (`products 0 rows products.jsonl`) plus the line naming
  the package. The count is read from the built package, so the printed number and the manifest's
  `counts` block cannot disagree.

## Ruled out

- An argument parsing crate (`clap`, `pico-args`): the surface is three flags and one positional, and
  the rule is that a dependency must save more than a page of safe code.
- A second binary (`furnicraft-export`): the task asks for one binary, and a second one doubles the
  release and packaging surface for one subcommand.
- Reading the catalogue from the file: the scene envelope never stores it (ADR 0095 and
  `docs/domain/scene-file.md`), and inventing a catalogue section would change the format for a job
  that already has the default catalogue.
- Treating every unknown first argument as a command error on macOS: Finder launches the app with
  `-psn_<serial>`, so that one prefix asks for the window like an empty argument list.
- Writing to a scratch directory and renaming the whole package: `write_dir` already documents that
  a caller who needs all-or-nothing renames itself; a CLI that renames over the caller's `--out`
  would delete what was there without asking.
