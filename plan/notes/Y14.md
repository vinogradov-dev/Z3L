The material window: what the tree gave, what the owner changed, and what the eyes found.

## What was measured

- `crates/materials` (L2) holds the whole vocabulary already: `Material { id, name, base, coat }`
  (`material.rs:334-449`), `Library` indexed by `MaterialId` with a duplicate id and a duplicate name
  refused (`library.rs`), `Store::read/write/picture/revision` (`store.rs`) and the wire form. Every
  range is validated where the record is built and a refusal names the channel
  (`MaterialError::Field { field: "base roughness", … }`), so the window states no rule of its own.
- `MaterialId` is zero-free and `Ord`, so a fresh id is the largest plus one: `Library::next_id`.
- The shell reads the folder once (`app/src/materials_watch.rs:open`) and watches its stamp off the
  frame path; `App::take_materials` hands one `Arc<Library>` to every tab, and a tab takes it through
  `Document::set_materials` → `Session::set_materials`, which moves `materials_version` and no
  document revision.
- A node names a record by `model::MaterialRef` (`crates/model/src/ids.rs:93`), read by
  `app/src/scene_build.rs`; nothing walked the tree for those references, and `Project` had no public
  node iterator — hence `Project::nodes_by_material` in `project/query.rs`.
- The settings window never writes a file: `ui::settings::show` returns an outcome and the shell
  applies and persists. The material window keeps that rule and goes further: `ui` never reads a path
  either, so the shell decodes the swatch's picture and hands it `ColorImage` texels.
- The picker carries one order per file kind (`app/src/file_picker.rs`), and `PickMode::Image` is a
  *save* dialog: choosing a scan is a new read order filtered to PNG, `PickMode::Picture`.
- The swatch's tiling is one quad with uv past `1.0` and `TextureOptions::LINEAR_REPEAT`, and the
  quarter turn is a rotation of the uv ring — one draw call, no tile loop, no seam.

## Decisions

- **The window, not a settings page** (the owner's ruling, 2026-11-26): a material is edited the way
  every graphics program edits one, from the render place, in its own floating window; the settings
  hold how the *workspace* looks. ADR 0251.
- **Deleting is allowed and the references stay** (the owner's ruling): the document keeps the
  `MaterialRef`, the frame draws that node with the default tone, and the window lists the id the
  documents still name in the danger ink — a click starts a record under that number, which is how a
  shop puts a material back on the objects that want it.
- **Live editing, one act per settled change**: a switch, a picture, a new or a deleted record is
  written at once; a number or a name waits `COMMIT_SECONDS` (0.4 s, the pause the one scrubbing field
  already uses). No *Apply* button: the renderers a shop knows apply a material as it is edited.
- The whole library is validated and written by the shell before any tab sees it, so a second record
  named `Oak` leaves `library.json` byte for byte as it was.
- A picture is chosen, never typed, and `Store::import_picture` copies it under a free name so one
  record never replaces another's scan; a file already in `textures/` is named in place because
  copying it onto itself would empty it.

## Ruled out

- A `Materials` page in the Settings window (Y14's first shape): the owner rejected the place. Nothing
  of the page's design was reused — it is a `Window`, not the modal.
- A *Delete* that refuses while a node names the record: the owner ruled the reference may dangle.
  The red row therefore lives in the window's list, because the object's own material slot is U129's
  and does not exist yet.
- `Window::order(Order::Foreground)` as a fix for the shot below: it changed nothing, and the default
  order matches the assistant panel.
- Letting `ui` call `Store::write` or `Store::picture`: file I/O and the picture copy stay in the
  shell, which is the one thing the settings window has never done either.

## What the eyes found

`app/src/ui_shots.rs` gains `the_material_window_is_painted_offscreen`, which writes
`target/ui-shots/material-window.png`: the list, the fields and the swatch with a 2 × 2 scan tiled at
150 mm over a 300 mm swatch, so the repeat and its turn are visible. Two things the rectangles could
not say: a coat-only record's chip was filled with the same ink as its stroke and vanished — it is the
control's ink now — and the place's *Press Render* line paints over the window in the shot. The second
is the shot pipeline, not the window: a probe that opened the **Settings** modal over the same place
showed the same bleed, so the headless `run_ui` root paints its own shapes after the areas'. Left as
it is, and named here so the next session does not chase it.
