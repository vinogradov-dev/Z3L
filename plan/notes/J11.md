# J11 — J11 — an agent process owns the model loop, and what the wire needed

J11 — an agent process owns the model loop, and what the wire needed

## What was measured

- ACP as published today (v1, `agentclientprotocol.com`, read 2026-11-23): the transport is the
  process's own stdio, one JSON-RPC frame per line; streamable HTTP is an RFD, not part of v1.
  `session/new.mcpServers` takes stdio entries (`name`, `command`, `args`, `env`) always, and
  `{type:"http"|"sse", url, headers}` only when the agent advertises `mcpCapabilities.http`.
- `mcp::channel` is a loopback socket behind a `token\n` handshake line and then newline-delimited
  JSON-RPC — not a streamable-HTTP MCP endpoint, so no agent can be handed `{type: "http"}` at it.
  `Channel::open` publishes `{port, token, pid}` to `<settings>/channel.json` at `0600`, which is
  where ADR 0188 itself says "a client learns the port".
- `z3l mcp serve --attach` *hosts* a channel from a CLI process; nothing in the tree consumed one,
  and `cli.rs` already spelled out that a later verb must not silently change what a line does.
- `mcp::dispatch` called `Session::agent_batch`, which opens its own scope: one channel batch, one
  undo entry. `Session::agent_batch_in(scope, …)` is the merge J7 added for one message.
- `ChatBackend` was `ask`/`take`/`waiting` over `Reply { text, calls, checklist }`: no way to report a
  tool call, and `Turn` ended the turn on any reply that named no calls.
- `AssistantSettings` held `attach: bool` and nothing else; the Assistant page drew one checkbox.

## Decisions

The record is ADR 0230; the four a later session will trip over first:

- **`z3l mcp bridge`, with no arguments.** It reads `channel.json`, presents the token and copies
  bytes both ways, so the token never enters the agent's argv or environment. It speaks no protocol:
  the tools, the plan gate and the history stay the window's.
- **`mcp::acp` behind a `Spawner` port.** `Program` starts a real command; `Scripted` hands in a peer
  on two OS pipes from `testkit::acp`. Two threads: a reader per process and one worker state machine
  on an event queue, so the window never waits on a pipe.
- **`Reply` gained `lines` and `more`**, `Speaker::Tool`, `Conversation::extend`, `ChatBackend::cancel`.
  A piece of an answer is drawn at once and keeps its request in flight; the stop becomes
  `session/cancel` on the frame it is taken.
- **`Door::Window { sink, scope }`.** A batch that arrives while a chat turn is open joins the turn's
  edit scope, and `Chat::scope()` is what the shell passes. The scope is the shell's answer and never
  a request field.
- **No fs, no terminal.** `initialize` advertises neither and refuses a process that asks.
  `session/request_permission` is answered with the first allowing option, because the plan switch is
  the real gate (`AGENTS.md` §4.11, ADR 0190).

## Ruled out

- **Streamable HTTP at the channel.** It is an HTTP server inside a tree that forbids a second web
  stack, and the bridge makes it unnecessary.
- **`mcp serve --attach` as the pipe.** `--attach` already means "host the channel here"; a client
  pipe is a different job and got a different word.
- **Per-connection client ids, so only the agent's own batches share the turn's scope.** The
  handshake carries no id, one window runs one turn, and the cost is written into the ADR.
- **Drawing only when the prompt response lands.** A minute of spinner for a process that is talking
  is the "unusable surface" J13 exists to catch; the `more` path costs ten lines.
- **Refusing `session/request_permission`.** An agent that is refused hangs, and it cannot outrun the
  window's own gate.

## What a next session should know

- The command is `AssistantSettings.agent`, one line split by `mcp::Program::parse` (program first,
  the rest are arguments). `App::apply_agent` runs in `App::frame` before `serve_chat`, starts one
  process per configured command and never per frame, installs nothing while the channel is off, and
  never replaces a backend it did not create — which is why the frame tests can install their own.
- Tests: `crates/mcp/src/acp.rs` (seven, over `testkit::acp` pipes), and in `app/src/frame_tests.rs`
  the two the task's Done clause names: `an_agent_process_turn_lands_one_undo_entry_and_the_panel_draws_its_calls`
  and `a_process_that_dies_mid_turn_leaves_the_document_as_the_last_batch_left_it`.
- Not done, and worth a task of its own: `session/load`, `session/modes`, `available_commands_update`
  and `agent_thought_chunk` are ignored; the panel has no "working" line of its own beyond Stop and
  the streamed chunks.
