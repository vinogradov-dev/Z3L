# J6 — the channel the window offers, and what a caller may learn from it

## What was measured

- `crates/mcp` has one door: `CommandServer` (`server.rs`) owns `Arc<Mutex<Session>>` and is served
  over a generic reader/writer pair (`lib.rs::serve`, `serve_stdio`). Nothing binds a socket: the
  lock file has no `TcpListener`, and the workspace `tokio` features are `rt, io-std, io-util,
  sync` — no `net`, no `time`.
- The window does not share one session: `app/src/document.rs` holds a `Session` per tab
  (`Document { session, editor, .. }`), and the active tab is `Tabs::active_mut`. A server that owned
  a session could not serve "the document a person is looking at" (the task's Why).
- ADR 0188 puts `--attach` in `mcp serve` ("two modes of one server", "`--attach` starts the local
  channel"), and ADR 0193 says the acceptance test starts "a child `z3l mcp serve` over stdio, and,
  once `--attach` exists, the local channel" — i.e. the flag is a headless door a test can drive.
  The window's own channel is the same module with no flag: "on by default and switchable off".
- The frame already takes work at its boundary: `App::frame` drains the directory worker
  (`take_directory`) and the file manager (`take_pick`) before anything derives from them, which is
  where ADR 0187's "a turn dispatches at a frame boundary" belongs.
- `Settings` (`crates/ui/src/settings.rs`) has no assistant section; the window's pages are
  `Appearance, Viewport, Panels, Shortcuts`. `SettingsStore::directory_root` is the folder beside
  `settings.json`, so the token file has a home the shell already owns.
- `getrandom` 0.3.4 is already in `Cargo.lock` (indirect); it is MIT OR Apache-2.0 and pure Rust.

## Decisions

- **One mailbox, one frame boundary.** `mcp::channel` owns the socket, the token and the handshake;
  a tool call becomes a `Call` queued to the host, and the host answers from its own thread.
  `Pending::answer` hides the `oneshot` so `app` never names `tokio` (ADR 0186 keeps the runtime in
  `mcp`).
- **The window answers as the active tab.** `Call::List`, `Dispatch` and `Ask` run against
  `tabs.active_mut().session`, so an agent edits the document in front of the person, and the
  answer's revision is that document's. A batch in the window is never written to disk: the report
  says `write: window`, because the person's Save is the write (ADR 0005, dirty marker).
- **`ui_inspect` is the shell's own state**, in a plain `mcp::Window` value the shell fills: the
  tabs (title, path, dirty, revision, product), the active index, the armed transform id, the
  selection and the status sentence. It is a report, not a second read model — the scene stays
  `query`'s.
- **The handshake is one line: the token, then `ok`.** MCP frames are newline-delimited JSON, so the
  first line of a connection is the token and the server answers `ok` before any frame is read. A
  wrong or missing token is refused and the socket closed without a `Pending` being queued — that is
  the "refused before it is read as a command" clause, and the test asserts the mailbox stayed empty.
  The compare folds every byte (no early return), and the read is one byte at a time with a cap, so
  a hostile peer cannot make the server allocate a line it did not ask for.
- **The file is `channel.json`, mode `0600`, minted once per run, removed on a clean exit.** It holds
  the port and the token and nothing else; a reader that cannot connect reads "no window is open"
  (ADR 0188). An existing file whose port answers means a channel is already up: `open` returns
  `Taken` and the second instance neither binds nor touches the file — the setting is on by default,
  so a second window is the ordinary case, not an error a person must solve.
- **`--attach` is a mode of `mcp serve`**, not a window flag: the window's channel is the settings
  switch (ADR 0188's "on by default"), and the flag gives a process a channel a test can drive
  headlessly. Its lifecycle is its standard input: the channel stops when the parent closes it.
- **A carried piece and a pending question are `busy`.** The dispatch happens between frames, so a
  drag cannot be interleaved; the two gestures that span frames are a piece in hand
  (`Document::holding_piece`) and a question waiting for an answer, and both answer "busy" instead
  of moving the document under the hand.

## Ruled out

- **One `Arc<Mutex<Session>>` for the window** (the headless shape): the window holds several
  sessions and swaps the active one, and a lock held across a frame would freeze the person.
- **The window writing its scene on a landed batch**: the tab is dirty on purpose, a path may not
  exist yet, and `z3l run`'s "write once at the end" is a headless promise. The answer says so
  instead of surprising the person with a file write.
- **HTTP or the streamable-HTTP transport**: it would add `hyper` and a second framing to a channel
  that only ever carries our own tools; MCP over the stream pair `serve` already takes is the same
  wire as stdio.
- **A token in a query string or an env var**: ADR 0188 puts it in an owner-only file, which is also
  the discovery mechanism — one artefact, one permission, one removal.
- **A signal handler for `mcp serve --attach`**: it needs a new dependency (or `unsafe`), and the
  parent's stdin is the lifecycle a spawned child already has.
