# U102 — What was measured

## What was measured

- `crates/ui/src/scene_tree.rs` already kept the selection as a `Vec<Id>` in click order with the
  last id as the primary (`Selection::ids`, `primary`), and `Editor::selected_nodes` already exposed
  it read-only, so the order a loft needs was there before the task: only the modifiers were not.
- A tree row read `ctrl || command || shift` as one `additive` flag and toggled on it
  (`scene_tree::select`), so both modifiers meant "add", and no surface read them in the viewport:
  `Editor::select_viewport_hit` took `(project, open_product, hit)` and always replaced.
- `crates/engine/src/session.rs` (the entry's third hint) holds no selection at all: it is view
  state and lives in `Editor` (ADR 0029), so the hint was stale and the task touched three ui files
  and one shell file instead.
- `crates/scene/src/lib.rs` `with_selection_highlight(&[Id])` already tints every selected drawable,
  and `Document::upload_scene` feeds it every top-most selected node, so a drawn multi-selection
  needed no renderer change.

## Decisions

- One `Pick { Replace, Add, Remove }` value with `Pick::from_modifiers`, public from `ui`, is the
  single decode site: the tree row and the viewport click both call it, so the two surfaces cannot
  drift into two meanings of Ctrl.
- Shift toggles (append at the end, or take the same node back out on a second click) and Ctrl only
  removes; Ctrl wins when both are held, because a slip of the other key must not re-add a node the
  person was removing.
- A modified click on empty space changes nothing; only a plain click clears the selection, so a
  missed Shift-click cannot silently drop a set built over several rows.
- The camera and light glyph path goes through `Editor::pick_node`, not `select_viewport_hit`: the
  glyph is already resolved and must not be re-resolved through the container rule.
- `Document::highlighted_nodes` exists only for the frame test (`#[cfg(test)]`) and returns the
  selection the last uploaded frame was built from.

## Ruled out

- Moving `Selection` from `crates/ui` into `engine::Session`: the entry's prose says "in the
  session", but `Session` owns document and history while the editor owns every view flag
  (ADR 0029); moving it would be an S-task, not a modifier change.
- A second selection type for "ordered" versus "unordered": the order was already stored, and a
  duplicate would have to be kept in sync on every delete and undo (`retain_existing`).
- Editing the mesh-vertex picker's `additive` flag in the same change: it has no ordered set and its
  own rules, so it stays as it is until a task measures it.
