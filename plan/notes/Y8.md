# Y8 — the render's materials are one portable library

the render's materials are one portable library

The render has to be independent — liftable into another project — and it has to follow the popular
renderers, so a material is a record of its own base and not a field of a catalogue item. The owner's
mechanism, 2026-11-25: the catalogue holds sheet materials (chipboard, glass, MDF) and decorative
coatings (paint, PVC film, veneer, lacquer), and **each names a material of the render's base**; the
viewport takes a material from that base and draws it simplified so the chipboard's texture is
visible; a panel card will name an **ordered list of decors** for the plate's face and for the edge —
a veneer, then a lacquer at 90 % — and the render composes the picture from those layers in that
order.

## What was measured

- `crates/catalog` is the nomenclature: `NomenclatureItem`, the `Directory` snapshot and the
  `FolderSource` port with `snapshot()`/`revision()` (`crates/catalog/src/source.rs:180`). It owns
  **no** file of its own and carries no picture: `view::COLOR_SLUG` is a *word* naming a decor
  (`"oak"`), never a colour. `docs/domain/nomenclature.md` §7 promises an `Appearance` block (colour,
  texture, roughness, metallic) that no code holds yet — O16 replaces it with a reference.
- `crates/scene` already carries what a frame needs: `Surface` (roughness, metallic, ior,
  transmission, absorption, `lib.rs:362`) and `Decor` (picture texels, `covers`, `Turns`, one `uv`
  projection both consumers call, `decor.rs`). `DecorId` is a non-zero `u64` whose doc says the
  number belongs to whoever builds the frame. `scene::Decors` did not exist.
- `crates/render` keeps one device picture per `DecorId` in a swept `SlotCache` (`lib.rs:674-732`),
  and `FaceKey` includes the decor, whose `PartialEq` is id/covers/turns. So **a replaced picture
  under the same `DecorId` is never re-uploaded**: a re-read must arrive under a new number. That is
  why `DecorId` is allocated and not derived.
- `app/src/settings_store.rs`: the settings file lives under the platform config directory, and
  `directory_root()` already puts the nomenclature folder beside it, so `library.json` and
  `textures/` join the same folder and a shop moves its workspace by copying one directory.
- `app/src/directory_watch.rs` is the hot-reload shape: a worker polls a stamp off the frame path,
  reads one validated snapshot, hands it over the channel; `App::take_directory` applies it to every
  tab. `Document` watches `session.directory_version()` to re-derive its frame and nothing else.
- `png` was already a workspace dependency (`final`'s writer, the interface shots) and decodes too, so
  a decor picture costs no new crate.
- Nothing maps a document node to a render material: `Panel::material()` is a catalogue `ItemId`, and
  the catalogue item has no library reference until O16. So Y8 cannot colour a panel, and the frame's
  decor is proved at the seam, not through a panel (see below).

## Decisions

- **`crates/materials`, L2**: `MaterialId` (non-zero `u32`), `Material` (name, optional `Base`,
  optional `Coat`), `Library` (validated, `BTreeMap` by id), `Store` (the folder: `library.json` +
  `textures/`), `Picture` (PNG → RGBA8), `Revision`. Dependencies: `units`, `serde`, `serde_json`,
  `thiserror`, `png`. No document, no scene, no renderer (ADR 0244).
- **The record is the renderer's channels and no more**, and it carries the coat, which is what the
  task text and ADR 0243 disagreed about: the ADR says "the record Y8 builds carries it", and O18
  needs a *finish* record whose group is the lacquer. So `base` is optional and `coat` is optional,
  and a record with neither is refused. A lacquer is a coat with no base; a veneer is a base with no
  coat.
- **The file**: `version`, `materials[]`, each with `id`, `name`, optional `base` and `coat`.
  Channels: `colour` (linear RGB `0..=1`, required — the decor multiplies it), `decor` (`picture` a
  relative path, `covers_um` in micrometres, `turns` 0..3), `roughness`, `metallic`, `ior`,
  `transmission`, `absorption` (`[f32;3]`, per millimetre); a coat's `weight`, `gloss` (percent) and
  `ior`. The five base channels a record usually omits default to the tracer's matte
  (`1.0 / 0.0 / 1.5 / 0.0 / [0;3]`), so a colour and a picture describe a board. A length is written
  `…_um` like every other file in the tree; a colour is linear like the scene file's light colours,
  and the doc comment says so.
- **Refusals name the record and the file**: a record with no name, a name past 120 characters, a
  record with no base and no coat, a channel outside its range (NaN and infinity included), a decor
  with a blank or absolute or `..`-escaping path, a decor covering zero, a turn past three, a
  duplicate id, two records whose names differ only in case or spacing (a shop cannot pick between
  them), a schema other than 1, a JSON error, and a picture the file names that is not there.
- **A picture's presence is checked at load; its texels are decoded on demand.** Thirty decors are
  thirty megabytes decoded; a window that opens a scene must not pay that. `Store::picture` decodes
  one record, and the frame's `Decors` calls it once per record per library revision.
- **`Store::revision` hashes the library file and every picture it names** (path, mtime, length, a
  missing file as zeroes), so a replaced scan moves the stamp although the file did not change.
- **`scene::Decors`** (new, in `decor.rs`): `follow(generation)` drops every entry when the library
  moved; `decor(key, load)` reads one `Picture` (image, covers, turns), builds the `Decor` with an
  **allocated** `DecorId` (a monotone counter, never reset), and remembers `None` for a record with
  no decor. `Picture` is the frame-side value the loader answers, so nothing in `scene` depends on
  the library's crate or its file.
- **The shell**: `SettingsStore::materials()` → the store beside the settings file;
  `app/src/materials_watch.rs` mirrors `directory_watch` (400 ms poll, 2 ms under `cfg(test)`);
  `App` carries both watches in one `Watching` value; a reload applies to every tab through
  `Document::set_materials`, and the tab re-derives its frame on `session.materials_version()`, never
  a document revision. A session that is born without a library names no material (an empty one).

## What landed

- `crates/materials/` — `lib.rs`, `id.rs`, `material.rs`, `library.rs`, `wire.rs`, `picture.rs`,
  `store.rs` (23 tests: round trip with every channel, the four named refusals plus the schema one, a
  replaced picture re-read, an absent file as an empty library, an unreadable picture, the save's
  temporary file).
- `crates/scene/src/decor.rs` — `Picture` and `Decors` (three boards share one picture and one id; a
  moved library re-reads a replaced picture under a new id; a flat record is remembered).
- `crates/engine/src/session.rs` — `materials`/`materials_version`, `with_materials`, `set_materials`,
  `materials_shared`; a test proves the swap moves no revision, no dirty mark and no history.
- `app/src/materials_watch.rs` (a replaced picture reaches the shell without a restart; a broken
  library is refused once) and the wiring in `settings_store`, `main.rs` and `document.rs`.
- `Cargo.toml`, `xtask/src/main.rs` (layer row), `PROJECT.md` and `AGENTS.md` (crate map), ADR 0244
  and its index row.

## Still open, and for whom

- **The panel card's ordered list of decors — face and edge — is not in the plan.** The owner
  described it as part of this mechanism, and neither Y7 (one record per board) nor O18 (a base and
  a finish) names a *list*. It needs a task of its own: document or catalogue data (an ordered list
  of material ids per face and per edge), the card, the command, and the frame merging the list into
  one `Surface` and one `Decor`. File it before Y7, which builds on the answer.
- **Nothing maps a node to a library material yet.** O16 puts the id on the catalogue item and Y7
  maps a board, a band and a handle onto `Drawable::color`, `Surface` and `Decor`; the seam Y8 left
  is `scene::Decors` plus `Store::picture`, one `Decor::clone` per drawable.
- **`z3l render` installs no library.** `cli/render.rs` builds its session from the scene file alone,
  so a headless image has no decor until the compound reads the workshop's store (Y7's edge, or the
  command's own when it learns a library path).
- **Nothing authors a record.** A shop writes `library.json` by hand and drops scans into
  `textures/`; there is no starter file, because a session must not invent a shop's boards. A card
  that edits a record is a later task and writes through the same `Store`.
- **PNG only.** A JPEG decor would be a new dependency and its own decision.

## Ruled out

- A record per finished surface (veneer × lacquer): O18's and ADR 0243's rejected alternative.
- A content hash on a decor picture: ADR 0149 pins a part document because a moved bore changes the
  holes a shop drills; a decor is replaced and not versioned, and a hash would refuse a new scan
  instead of drawing it.
- Decoding every picture when the library loads: thirty scans is more memory than the whole frame.
- Deriving `DecorId` from `MaterialId`: the renderer and the tracer keep a texture under the id until
  the frame stops naming it, so a replaced picture would never reach the screen.
- Putting the library in the scene file: a shop's materials are the workspace's, like the directory
  and the settings, and a scene must travel between shops without them (ADR 0148, ADR 0244).
- A fallback material when a record is missing: a missing record stays a diagnostic (ADR 0148), and
  Y7 keeps the shell's placeholder tone until then.
