# J24 — What was measured

## What was measured

- **The chat was one field on the shell.** `App::chat: Chat` held the conversation, the backend, the
  turn, the edit scope of that turn and the gateway session id, so two open scenes shared all five.
  `App::answer_channel` read `self.chat.scope()`, which means a batch a process landed while another
  scene was in front joined *that* scene's history or none.
- **The panel's flag sat in the same value.** `Chat::open` was one field beside the transcript, even
  though the window itself is one `egui` area (`Id::unique("assistant_panel")`) and its rectangle is
  workspace memory. Two facts with two owners were one field.
- **`serve_chat` drove the one chat with the active tab's session**, so "whose turn is this" was
  whichever tab happened to be in front on the frame that advanced it.
- **An agent process does not go through the turn.** `Acp` spawns the configured command, hands it
  `z3l mcp bridge` as its one MCP server, and that bridge presents `channel.json`'s token to the
  window's socket (`mcp::channel::bridge_stream`). Its tool calls are `Call`s the window answers in
  `answer_channel`, against `self.tabs.active_mut()`. The `MessageDoor` inside `Turn::advance` serves
  the OpenAI backend's calls; the process's calls never pass it.

## What was done (ADR 0233)

- `Chat` moved into `Document`, which is the tab payload: conversation, backend, turn, scope, session
  id and the cached findings are the tab's. `Chat::new()` builds one per `Document::new`.
- `Chat::open` became `App::assistant_open`, one workspace flag written by the header's cell and by
  `Ctrl+J` through the one `App::toggle_assistant`. `Chat::show` takes `&mut bool`, so the window's
  close button and the flag are still one act and the egui id (and therefore the position) is one.
- `App::apply_assistant` applies the workspace's program, problem and endpoint to **every** tab, so a
  scene that comes forward is already able to send. A tab mid-turn still keeps its backend.
- `App::serve_chat` serves only the active tab: `document.chat.serve(&mut document.session, lang)`.
  A turn in a background tab advances no step and its reply stays in flight.
- `App::chat()` / `App::chat_mut()` are the only doors to the active tab's chat; every call site in
  `main.rs` and `frame_tests.rs` goes through them.

## The gap this task does not close

An **agent process** owns its own loop, so leaving its tab does not pause it. Its calls reach the
window's one channel, and the channel answers the **active** document — that is the channel's
contract for any client (ADR 0188), and `Call` carries no tab. So a background process can land a
batch in the front scene. Fixing it means the bridge, `Call` and `answer_channel` carry the tab that
asked (an optional field, or one channel per tab), which is a change to the tool server's contract
and needs its own task and record; it is filed in `plan/debt.md`. The turn itself — the transcript,
the answer, the undo entry — is the tab's and does not mix.

A second, smaller consequence: two tabs that both sent a message run two backend workers, and for
the process kind, two processes. A tab that never sent one starts nothing, because `Acp` spawns on
the first message.

## Tests

`app/src/frame_tests.rs`: `each_tab_holds_its_own_conversation_and_its_own_backend`,
`a_turn_pauses_when_its_tab_leaves_and_finishes_when_it_comes_back`,

(601 passed), `cargo clippy --manifest-path app/Cargo.toml --all-targets` is clean.
