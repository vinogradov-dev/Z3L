## What was measured

- `apps/furnicraft/src/scene_build.rs:349` — `SubtreeBounds { all, solid }` is computed per container
  in `Evaluation::collect` and thrown away; `evaluate` returns only the scene-wide `Bounds`.
- `apps/furnicraft/src/document.rs:754` — `refresh` rebuilds on revision, visibility, preview and
  `active_product`; opening a group moves none of them, so a frame-baked bracket would go stale.
- `crates/ui/src/editor/selection.rs:59` — `Editor.open` was private with no accessor; the shell now
  reads `Editor::open_containers` (22:37 edit).
- `crates/ui/src/theme.rs:141` — U83 already declared `HELPER_OPEN_STROKE` (2 pt) and the `helper`
  ink for exactly this bracket, so the task added no colour and no width.
- `crates/ui/src/scene_gizmo.rs:311` — the sibling paint: per view, `ui.painter().with_clip_rect`,
  `screen_point` from `gizmo_math`; no `Area`, no order, no pick.

## Decisions

- **The box travels as `[DVec3; 8]`, not as `Bounds`.** `Bounds` has private fields and no public
  constructor, so a paint module could neither build one in a test nor read a corner. `LevelBounds`
  carries `Option<[DVec3; 8]>` in one documented bit order, and `OpenBoxes` reads the open product's
  envelope in the same order, so a container and a product bracket alike.
- **The tab keeps one box per container from the last rebuild.** Filtering by the live open set at
  paint time is what makes opening a level free: no revision, no preview, no rebuild.
- **A product comes from the frame it already drew.** `ProductEnvelopeState::Open` is that same open
  state, and the envelope is oriented on the product's own frame; re-deriving it would be a second
  owner of one box.
- **Arm length per corner, one length for its three arms.** `clamp(shortest projected edge / 5, 6, 18)`
  is read at 2000 mm as the saturated 18 pt and at 12 000 mm as the 6 pt floor; an edge under half a
  point is end-on and draws no arm, which is what a plan view needs.
- No ADR: ADR 0111 already decided the ink, the widths and "a guide is screen space".

## Ruled out

- **Baking the brackets into `SceneFrame`.** It would tie an opening to `refresh`'s rebuild keys and
  evaluate the scene to expand a tree row; the bracket is view state the frame never stores.
- **Re-using `scene_gizmo.rs`.** It picks glyphs and reads the document; the brackets pick nothing and
  read the last evaluation, and that file is already 342 production lines (the S7 audit's ceiling).
- **`egui::Area` on `Order::Middle`.** The paint sits in the viewport's own `Ui`, after the image and
  before `scene_gizmo::paint`, which is the order the entry asks for and needs no host (`ui-rules`'s
  `HOST_OWNERS` gains no row).
- **Following a drag preview.** The bracket stays on the committed box during a move; filed as
  `[gizmo]` debt rather than threaded through `Evaluation`, which takes no panel or object preview.

## The cheap path

One sentence in the entry: "`Evaluation::collect` computes a `SubtreeBounds` per container and drops
it; carry it out of `evaluate` as `LevelBounds` and read `Editor::open_containers`." It belongs in the
Shape, beside "the shell collects the bounds", because that clause was the whole plumbing cost.

## For the strategy

A Shape that prescribes the paint but not the data path sends the session through three modules to
invent one; the entry should name the value that has to start travelling. The harness is sound — the
frame test and `ci` were green first try — so the cost of this task was finding the box, not writing
the bracket, and the log's `read`/`dead-end` columns are where that shows.
