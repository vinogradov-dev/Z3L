# N19 — The frame's box is the box tool's, and its pull is the lettered plate.

The frame's box is the box tool's, and its pull is the lettered plate.

## What was measured

- `BoxDraft` (`crates/ui/src/box_tool.rs`) was two tools in one value: the first and live corners of a
  rectangle it built from its own plane clicks, and the fixed base (rectangle or ring) with the pulled
  height. `Document::update_box` mapped the pointer onto the plane every frame for the live corner and
  `app/src/box_gizmo.rs::paint_box` drew that live rectangle in `BASE_COLOR` — one of its six paint
  branches belonged to the second rectangle tool.
- The cuboid cell (`ToolKind::Body(DrawTool::Rectangle)`) already armed the sketch draft
  (`Editor::start_body_drawing`): the base plates are `PointState::rows`, two `PointRow`s labelled `W`
  and `H`, typed through `FieldSet` and placed with Enter or a click.
- The frame's pull drew `ToolView::height(Message::FrameHeight, …)` — a title word, `mm` beside the box
  and the ✓/✕ pair — while the solid's pull drew `ToolView::pull(…)`, the one lettered `H` plate with
  `ToolCommit::Keys` (U104). The owner read that pair of cards as two tools.
- `Envelope::with_ring` anchors the ring and stores `Footprint::Ring`; `Envelope::new` stores nothing,
  and `BoxBody::grips` (`app/src/box_gizmo.rs`) gives a ring only its two height faces while a
  rectangle keeps eight corners and six faces. The stored footprint therefore decides which grips the
  maker gets.
- `crates/ui/src/editor/drawing.rs::start_product_pull` already closed a frame's figure, so the ring
  path (ADR 0159) needed no new plumbing — only a second way of reading the figure.

## Decisions

- **One arming path.** `ToolKind::ProductBox(DrawTool)`, `DrawIntent::ProductBox`,
  `Editor::start_product_box_drawing` and `ToolAction::DrawProductFrame { tool }` carry the sketch's
  method into the frame cell, whose `furniture.product.frame.draw` row now runs
  `ProductBox(DrawTool::Rectangle)` — the same tool the `model.primitives.cuboid` cell runs. The ribbon
  activity is `ToolActivity::ProductBox(tool)` while the base is drawn and `ProductFrame` while the
  height is pulled.
- **The method decides the shape, not the geometry.** `start_product_pull` reads
  `DrawTool::Rectangle`'s figure as the plain box — bounds are the sides, the minimum corner is the
  frame's zero — so a drawn rectangle reserves `Envelope::new`, keeps its corner grips and is the same
  document the card writes (`the_card_and_the_drawn_gesture_produce_the_same_document` still holds).
  Every other figure stays the ring it was drawn as, including a rectangle drawn with the free outline:
  that method promises a shape rather than a box (ADR 0159).
- **`BoxDraft` is the base and the height.** `Base::{Rectangle, Ring}`, `from_rectangle`, `from_ring`,
  `base_corner`, `sizes`, `ring`, `set_height` and `envelope` — the last now returns
  `Result<Envelope, EnvelopeError>` because a draft without a base cannot exist. `first`, `live`,
  `click`, `set_live`, `base`, `is_pulling`, `BoxDraftError::FlatBase` and `NoBase` retire; `NotStarted`
  names the one refusal left.
- **The pull starts at its floor.** `START_HEIGHT` is `MIN_BOX_HEIGHT_MM`, so the plate never shows a
  number below its own range and the first commit cannot fail on a zero height.
- **The accept is the pull's own.** `box_gizmo::update_box` answers whether the click accepted the
  height; the `BoxEvent` enum and the plane clicks retired with the second rectangle tool.
- **The plate is the solid's.** `Document::height_view` builds `ToolView::pull(height, None, …)`, so a
  frame's pull draws `H`, no unit and no button pair, and Enter, a click and the field's own Enter are
  the commit path (`apply_tool_outcome` already routed Apply to `finish_box`).

## Ruled out

- **Sending the rectangle through `from_ring`** (the fewest lines): it stores `Footprint::Ring` for a
  plain box, so the drawn frame loses its corner grips and stops matching the card's document. The
  stored shape is not an implementation detail; it is what the grips read.
- **Keying the conversion on `PathShape::Rectangle`**: `Path::rectangle_from_edge` (the tilted method)
  tags `Rectangle` too, and a tilted rectangle's bounds are not its sides. The tool says what figure it
  promised, so the tool is what the conversion reads.
- **Keeping the titled plate for the frame** (`ToolView::height`): it is the surface the owner called a
  second tool. It stays in the card as one of ADR 0119's three commit states and is covered by
  `tool_card`'s own tests; nothing ships it now.
- **Teaching the pull the keyboard in this task** (`Document::tool_focus`): the height is still typed
  only after a click, exactly as before, and the `[ui]` debt row that names the slot stays true. It is
  the same ask `ExtrudeGizmo::take_focus` makes, and it is one change for both pulls, not half of it
  here.
