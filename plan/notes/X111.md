# X111 — the window that painted only when the pointer entered it

the window that painted only when the pointer entered it

## What was measured

- `app/src/main.rs::frame` called `serve_channel` at the top of every frame, so a call was answered
  only by a frame that had already started; nothing woke the window when a call arrived. `egui` gives
  a frame back only when it is asked for one, or when an input event arrives, which is why the cube
  appeared when the pointer entered (owner report 2026-11-21; the 83 s, 53 s and 196 s timings X107
  filed are the same wait).
- The queue is filled on the channel's thread (`AttachedServer::queue` → `mpsc`) and drained on the
  window's (`Mailbox::drain`). Only the drain can answer, so the fill had to ring it.
- `Mailbox` had no way to reach the host: `take`, `wait` and `drain` only. `Channel::open` published
  the port before anything could ring, so a client could connect in the gap.
- The headless door (`app/src/cli/served.rs::attach`) polled `mailbox.drain()` every 2 ms — no
  pointer, but a clock, and 2 ms of latency per call.
- Precedent for the seam: `app/src/file_picker.rs::Picker::start` spawns a worker that ends with
  `ctx.request_repaint()`, and ADR 0182 says "nothing polls and a still window costs nothing".
- `mcp` is forbidden `egui` (`cargo xtask layers`, ADR 0186), so the wake could not be a `Context`.

## Decisions

- `mcp::Wake = Arc<dyn Fn() + Send + Sync>` and one `Bell` per channel: the socket rings after every
  queued call, the host installs the wake once (`Mailbox::watch`). The window passes
  `Context::request_repaint`, which `eframe` turns into a `winit` wake (ADR 0225).
- `Bell.early` rings when the host starts watching after a call arrived, because the port is
  published before the wake is installed and a client can connect in that gap.
- The frame that answers a dispatch, and the frame that holds one, asks for the frame after it; a
  read asks for none. The shell counts frames and logs which one answered a call, so the frame that
  landed a change is named rather than guessed.
- The headless loop waits on the bell (`std::sync::mpsc::recv_timeout`, 50 ms) instead of sleeping
  2 ms: a call wakes it at once, and the timeout only notices a closed stdin.
- `Mailbox::post` is the test seam, `#[doc(hidden)]` like `queued`: it queues through the same bell
  the socket uses, so a frame test drives the real path with no client, no socket and no runtime.

## Ruled out

- **A timer in the window** (`request_repaint_after` every frame, or a 60 Hz idle repaint). It would
  have made the report go away by keeping the frame path busy: ADR 0140 already pays "a frame every
  frame" for the on-screen display, and a still window must cost nothing.
- **Letting `mcp` see `egui`** to call `Context` itself: forbidden by the layer table and ADR 0186.
- **Polling the mailbox in the window's own frame at a short interval**: the same clock as the
  headless loop, in the one place the plan says must stay free of document scans.
- **Asserting the repaint on `ViewportOutput::repaint_delay`.** Measured: the headless frame reports
  0 ns on every idle frame because `egui`'s own widgets (scroll areas, areas) ask for frames of
  their own, so the delay says nothing. `Context::repaint_causes` names the file that asked and lags
  one pass, which the frame test reads on the next frame.
- **The assistant turn's own repaint.** `serve_chat` drives one step per frame and asks for no
  frame, so a turn advances with the pointer too; it is a separate gap (the panel and its turn are
  X122) and is filed in `plan/debt.md` rather than widened into this task.

  the next one from the shell's own file.
