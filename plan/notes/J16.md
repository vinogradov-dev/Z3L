# J16 — What was measured

## What was measured

- `crates/mcp/src/tools.rs` declared `params` twice (`RunRequest::params`, `StepRequest::params`)
  as a bare `serde_json::Value` with `deserialize_with = "params_of"`. The schema schemars derives
  from `Value` carries a description and `default: {}` and **no `type`**: a caller that reads the
  schema learns nothing about the shape.
- Measured through `parse::<RunRequest>` and `mcp::dispatch` on the sample product: `params:
  "not json"` reached the command and answered ``invalid parameters for `panel.create`: invalid
  type: string "not json", expected struct PanelCreate``; `params: "[]"` (which J28 parses to a
  JSON array) answered ``invalid length 0, expected struct PanelCreate with 8 elements``. Neither
  sentence names `params`, the object, or `command_list`, and both name a Rust type.
- `params: {"bogus": 1}` already answers ``unknown field `bogus`, expected one of `parent`, …`` —
  the command's parser names the key, so that half of the task is a regression guard, not a fix.
- J28 (`fc82cdd`) parses a string that holds JSON into that value and leaves a string that is not
  JSON alone. That tolerance is right and stays; the bug is what happens when the value the string
  holds is not the object a command takes.

## Decisions

- **The envelope states its own rule, in `params_of`.** The value after the optional string parse
  must be one JSON object; anything else is `serde::de::Error::custom` with
  `` `params` is one JSON object whose keys the command's own schema describes, not <kind>; read
  that schema with `command_list` and the command id, and send the object ``. Both doors that call
  `parse` — the headless server and the attached channel — and the chat's `BatchCall` (which
  reuses `StepRequest`) get the sentence from one place, before any step runs.
- **The schema says `type: object`.** `#[schemars(extend("type" = "object"))]` on both `params`
  fields, and the doc comments now say the keys are the command's own and name `command_list`. The
  field's description is the schema's description, so no second table.
- **The caller's word for the value.** `value_kind` reads the parsed value a string holds, so a
  string that holds `[]` is "an array" — the value that reached the parser, which is what the
  expression is about. The string itself is not echoed: the caller knows what it sent.
- **The unknown key stays the command's sentence** (ADR 0198: the refusal is the command's own).
  Only the envelope's own mistake is answered by the envelope.

## Ruled out

- **Rewriting the sentence in `report.rs`.** It would know the step number, but the report is the
  wire projection of `BatchReport`; the chat panel reads `BatchReport` through `chat::describe`
  and would keep the Rust sentence, so the fix would cover one of three doors.
- **Changing `CommandError::InvalidParams` in `engine`.** Every command builds it from its own
  parser message (13 call sites), and the engine cannot see the wire's `params` field without
  turning a document sentence into an envelope sentence. The envelope is the tool layer's.
- **Refusing in `CommandServer::call` and `channel::intent`.** Two copies of one rule, and the
  `BatchCall` of the chat would still miss it.
- **Leaving the schema free-form and stating the shape in the description only.** A model reads
  the `type` keyword first; the description alone was what the measured caller had already
  ignored.
