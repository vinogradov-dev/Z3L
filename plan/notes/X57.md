# X57 — an edit uploads the drawables it changed, not the frame

## What was measured

- The upload used to build every buffer of the frame on each revision: a vertex and an index buffer
  per drawable, one flattened edge list over every mesh edge, and the grid, the chains, the product
  envelopes and the contact shadows. `app/src/scene_build.rs`, probe
  `an_edit_uploads_one_drawable_and_not_the_scene`, real adapter, 1280 x 800 target, best of five:

  | drawables | cold upload | unchanged frame | one edit | whole frame after the edit |
  |---|---|---|---|---|
  | 500 spheres | 107 ms | 0.17 ms | 0.26 ms | 102 ms |
  | 2 000 spheres | 375 ms | 0.89 ms | 0.92 ms | 371 ms |

  "Whole frame after the edit" is the same edited frame uploaded into an empty renderer, which is
  what every edit cost before this task. The edit is one new vertex and index buffer pair, one new
  edge buffer, and the sweep of the slot the old transform held.
- `scene::Drawable.mesh` is an `Arc<MeshData>` shared with the evaluation cache (ADR 0053), so a
  mesh handle survives a rebuild and identifies "the same geometry" across uploads.
- The flattened edge list had a per-frame budget of 4 000 000 line vertices, so a 5 000-sphere
  stress scene drew the wireframe on about 1 400 balls (X60). With one buffer per drawable that cap
  is per drawable and the frame no longer truncates.

## Decisions

- A key holds the `Arc` it compares by address (`cache::PlacementKey`, `FaceKey`, `EdgeKey`). The
  slot therefore pins the allocation, so an address freed by a delete can never be reused by an
  unrelated mesh and answer for it; `sweep` drops the pin with the slot.
- Faces are keyed by mesh, transform and colour, because a selected drawable's vertices carry the
  highlight ink. Edges are keyed by the edge list, transform and ink, because a line carries the
  viewport's ink, not the object's colour — a theme switch rebuilds the lines and leaves the faces.
- The edge list belongs to the drawable and is drawn per drawable in both edge styles. The hidden
  style already walked the drawables; the visible style now does too, so a dense frame pays one draw
  call per drawable instead of one, and no upload copies a concatenated list.
- The grid, the chains, the product envelopes and the shadows are keyed by their whole input
  (`cache::Rebuilt`), which clones the input only when it rebuilds.
- A drawable's centre is measured from the vertices the upload already built, not by transforming
  every position a second time (`geometry::vertices_centre`).
- `cache::SlotCache` holds no wgpu type, so the reuse rule is asserted headless; the buffer identity
  itself is asserted in `cargo test` through wgpu's noop backend (the `noop` feature is a
  dev-dependency of `render` and the test asks for `Backends::NOOP`).
- An edge list past the vertex budget is refused by name (`RenderError::EdgeListTooLarge`) instead
  of being cut, because X60's point was that a short wireframe is a wrong picture.

## Ruled out

- One buffer per unique mesh plus a per-drawable transform in a uniform slot: the camera uses a
  dynamic-offset uniform with four slots, and a uniform binding is capped at 64 KiB, so thousands of
  per-drawable slots need a storage buffer or instancing — a larger change than this task, and the
  one to make when a moving object's re-upload is measured to matter.
- Keeping the frame-wide edge list and concatenating cached per-drawable slices: a full memcpy of
  every line on every edit (128 MB at 5 000 spheres) and X60's per-frame cap would remain.
- Hashing the frame's inputs as the cache key: a collision draws a stale buffer, and the comparison
  is cheaper than the rebuild it prevents.

## Left for the owner

- X60's entry was written against the flattened frame list. That list is gone, so the truncation it
  describes no longer happens and its test (a line list of more than 4 M vertices split across
  buffers) describes a shape this code does not have. The remaining honest gap is a single
  drawable whose edge list exceeds one buffer, which is now a readable `EdgeListTooLarge` refusal
  rather than a chunked draw; X60 should be re-scoped or closed.
- The measurement above is the offscreen upload path with a real adapter, not a window with a
  cabinet: the live-window number the entry asks for is still the owner's five-minute check.
