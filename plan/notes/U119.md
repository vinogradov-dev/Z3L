# U119 — What was measured

## What was measured

- `model::SnapAnswer::point` was documented as "on the sketch plane" and was the 3D candidate:
  `Project::snap` returned the scene mark itself for every kind, so each consumer decided what to do
  with the height of the candidate. The sketch took its footprint (`draw_gizmo::snap_cursor`), the
  ruler took the point, and the marker was drawn at the candidate in both. That split is the defect
  the owner reported twice: T17 moved the marker, not the point.
- The only test of the marker compared it with the pointer (`< 24 pt`), which passes with a marker
  180 px from the point the click stores. Nothing asserted the two agree.
- The contour editor and the vertex editor build no `SnapRequest` at all: no resolver, no marker.

## Decisions

- **Two modes, in the model.** `SnapMode::{Space, Foot}` is the workspace's choice — 3D and 2.5D —
  and `SnapTarget::{Free, InPlane, Foot}` is what a tool declares in its request. The resolver
  returns the point the tool stores, so the marker has one place to stand.
- **A refused candidate is dropped before its kind ranks.** `nearest_point_to_ray`,
  `nearest_on_lines` and `nearest_on_arcs` take an `accept` closure, so a 3D sketch whose nearest
  corner stands off its plane still answers the next corner of that kind instead of falling through
  to the edge kind.
- **"On the plane" is the document's quantum.** `ON_PLANE_MM = 1e-3`: a candidate within a
  micrometre counts as lying in the plane, which is what a placement's arithmetic leaves.
- **This commit keeps the 2.5D reading for the sketch**, now consistent end to end (marker = stored
  point = the perpendicular foot), and it is the reading the owner named as useful for a top view.
  The workspace switch and the 3D plane of the first click land in the next commits of U119.

## Ruled out

- Leaving the mode to the app: that is how the footprint became a hidden default in the first place.
- Filtering the answer after the ranking: it loses the second candidate of the same kind (a board's
  upper corner off the plane hides its lower corner in it).
- Making the marker follow the pointer instead of the point: the pointer is not what the click takes.
## What the second session measured

- The mode had no surface: `SnapMode` existed with two variants and `#[default] Space`, the sketch
  hardcoded `Foot`, and nothing could choose. Wiring the mode in made that default visible at once:
  the frame test that walks a body's corners, edge middles and face centres went red, because with
  3D by default a sketch captures nothing of a scene that stands above the drawing plane.
- `WorkPlane::from_camera` is world XY (z = 0) for every view but an axis-aligned orthographic one,
  so "3D by default" would have meant "no corner of the furniture, ever", until a sketch can take
  the plane of the face under its first click — which the owner filed as a task of its own (U121).
- The contour editor mapped the pointer to the node's local XY plane and nothing else: no request, no
  marker, no capture. The vertex gizmo measured only the handle's own distance along one axis.
- The plan verbs could not clean up a mis-filed entry: `task drop` removed the stream's session note
  whenever the file existed, so dropping any app-stream task deleted `plan/SESSION.md` and the gate
  then refused the write. Fixed in `state-contract` with a regression test (`715e8d9`), because the
  plan could not be repaired with the tool otherwise.

## Decisions

- **The fresh default is 2.5D** (the owner's answer to question 1). The drawing plane is the world XY
  in the views a furniture maker works in, so the 3D reading out of the box would capture nothing
  above it; the shadow a board casts on the plane is the working reading, and 3D is the switch.
- **The face-under-the-first-click plane is U121**, not this task (the owner's answer to question 2).
- **A vertex drag answers every kind with the point itself** (the owner's answer to question 3: a mesh
  vertex is part of a 3D body). The tool declares `Free` on the plane through the point it carries,
  the dragged point lands on the candidate, and the workspace's mode does not apply to it.
- **The grid kind is left out of both editors.** It rounds wherever the pointer is, which is the
  drawing plane's quantum for placing a new point; a 60.5 mm side would land on 60 the moment it was
  dragged, and a vertex belongs to a solid, not to the plane.
- **The contour's marker is read from the working copy**, not from the resolver's answer: an
  along-contour drag projects the point onto its arc, so the answer and the stored corner differ by
  construction, and the marker must name the corner the drop writes.
- **One snap choice, one write.** `Document` keeps the kinds and the mode as one `SnapChoice`, so a
  cell press or a Settings edit reaches the file and every tab in one step.

## Ruled out

- Keeping 3D as the fresh default and waiting for U121: the first launch would refuse every corner a
  maker points at, which is the report this task closes.
- Snapping the vertex along its axis (a 1D projection of each candidate): the owner's answer is the
  3D reading — the vertex lands on the candidate itself.
- Leaving the grid in the editors: the two frame tests that drag a corner to a measured point failed
  on exactly that, and the rounding is not what an edit of existing geometry means.
- A separate `SnapTarget` for the editors: `Free`, `InPlane` and `Foot` already say what a tool can do
  with an answer, and the mode chooses between the two plane-bound ones.
