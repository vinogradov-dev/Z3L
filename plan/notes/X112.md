# X112 — a created frame is closed, and the first part after it is refused

## What was measured

- `product_create_run` (`crates/engine/src/product_cmds.rs:78`) calls `Project::add_product` and
  nothing else, and `Session::run` installed the new document without touching `active_product`, so
  `product.create` over the channel answered `open_product: null` and the first `panel.create`
  after it had a closed piece to write in. Reproduced 2026-11-22 in `crates/mcp/tests/served.rs`:
  `{"created":[5],"effect":"landed","open_product":null,...}`.
- Only the window opened a created frame: the card and the drawn frame in
  `crates/ui/src/editor/creation.rs` called `session.open_product(id)` after the dispatch, so a
  person's flow was right and every other door had to invent a second step nobody offered. ADR 0100
  already words the act ("a frame is created open"); ADR 0226 removed the command's guard, which
  made the first part writable but left the workspace closed.
- A batch runs its steps on a trial copy (`Session::trial`) and `Session::land` installed only the
  document, so a view state a step changed was dropped with the copy.

## Decisions

- The session opens the piece a command created, inside `Session::run`
  (`follow_created_product`), by asking the document whether the created node is a product. No list
  of the commands that create one, so a creation path added later follows the same rule.
- A landing batch takes the trial's `active_product` back with its document, so a batch that makes
  a frame leaves it open exactly as one dispatch does. A dry run and a rolled-back batch change no
  view state, because nothing lands.
- The UI's two `session.open_product` calls went away: the rule has one owner, and the shell only
  arms and selects the frame it just made. The existing `retain_active_product` keeps the undo and
  delete paths honest.
- The guide's first step names the rule (`guide()["steps"][0]`), so a caller reads it from
  `command_list` instead of finding the closed frame by trying it.

## Ruled out

- Opening in the tool surface after the batch: three doors (the window, the command line, the
  channel) would each carry the same two lines, and the session already knows what it created.
- A `CommandSpec` flag saying "creates a product": a second list to keep in step with
  `add_product`, when the document itself answers the question.
- Opening on redo: a redone product arrives through a document restore and not through a creation,
  and the person who undid it is the one who decides to work in it again.
