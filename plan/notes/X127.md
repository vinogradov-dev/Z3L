# X127 — What was measured

## What was measured

- A request for one cube spent the turn on four refusals: `unknown field size_um`; `missing field
  placement`; `missing field rotation`; `invalid type: map, expected an array of length 3`; then
  `invalid length 3, expected an array of length 4`. The wire shape is
  `{"translation":[x,y,z],"rotation":[x,y,z,w]}` with a unit quaternion (`PlacementWire`).
- After the shape was guessed, the model created nine bodies, one per answer, and stopped at
  `MAX_CALLS` (12). The prompt said "one command_batch" but not what a box is.

## What was decided

- The guide gains a `placements` row: the shape, the example `[0,0,0,1]`, millimetres for the
  translation, and the rule that a placement is this object, never a bare array.
- The system prompt states the same and adds: one box is one `object.cuboid.create` with all three
  sides, never one body per face. The model already had the root id from X125.
- Tests hold the guide row and the prompt line; the guide is served to every door, so the CLI and
  the MCP client read the same shape.

## What was ruled out

- Putting every command schema in the system message: J15 measured the catalogue at 189 989 bytes;
  the placement shape is the one the model guessed.
- A server-side guard that refuses a second identical box: the model may legitimately create
  several; the prompt and the schema are the fix, and a guard would invent intent.
- Raising `MAX_CALLS`: it is a safety limit, not the cause; the cause was four refusals and a
  repeated body.
