# G4 — the areas a drawing encloses, and the pull that takes one

## What was measured

- `crates/geom/src/boolean.rs` already owns the exact overlay of ADR 0043, and every result is
  ordered by position, so a partition built from it is deterministic whatever order the rings are
  given in. Nothing composed the three operations into the *faces* of a drawing.
- `crates/model/src/object.rs` stores a `Contours` of validated closed rings, `path.to_contour()`
  per ring, and `ContourSegment::from_geom` is the one-way conversion back — the boolean command
  already built a `Path` from a result ring with a private `path_of_ring`, which is now
  `Path::from_geometry` in `model`.
- `crates/kernel/src/lib.rs` `Profile` carries holes, and `param::machining` builds a panel's core
  with them, but the **document** does not: `Constructive { path, features }` is one ring, so a body
  cannot stand for a face with a hole.
- `param::constructive::compile_cutter` extends a *cutter's* sweep by 1 µm at each end precisely
  because a boolean between bodies that share a face answers nothing, so a hole drawn as a
  subtraction step is representable — and wrong for a pull, because a step's tool height is frozen
  when it is stored while the body's own height is what the arrow changes.
- `app/src/extrude_gizmo.rs` `Body::read` already refused `Geometry::Contours` with the comment that
  a set is extruded area by area, which is this task; `Pull` already carries an `EditScope`, which is
  how `start_created` reuses the arrow instead of writing a second one.
- `crates/ui/src/void.rs` is the pattern for a read-only atom: a point from the shell, a model query,
  a refusal word, no revision. `crates/ui/src/inventory.rs` demands one row per registered command
  and one *drawing* per row, so the area row carries no icon of its own.

## Decisions

- **The partition is `geom::partition_regions`**: the material is the union of the rings, then every
  ring splits every face. Starting from the union, not from one ring, is what makes the result
  order-independent — splitting only ring 1 leaves the annulus missing when the inner ring comes
  first. `MAX_PARTITION_FACES` refuses a drawing that would leave more than 64 faces.
- **An area is named by a point**, not an index: an index exposes the derivation's order in a public
  parameter, and the point is what the pointer measured. The command re-derives with the same code
  the atom used.
- **The body is created on the click, inside an edit scope**, then the existing arrow adjusts its
  height in that scope (the cone's shape, ADR 0141). Creating at the ✓ instead would need a preview
  of a node that does not exist, and `Preview` is keyed by node id.
- **A face with a hole is refused** rather than cut by a subtraction step (see below). The atom still
  highlights it, in the warning ink, and the status bar prints the sentence: a maker sees what the
  pointer rests on and why the click will not take it.
- **The highlight is paint, not the session overlay.** ADR 0093's overlay replaces one node's
  geometry; the highlight is drawn *beside* the drawing, and a picture that replaced the set with one
  ring would hide the rest of the drawing.
- **D2 the cache lives in the atom** (`(drawing, revision) -> faces`), because the engine command
  re-derives once per click and the shell reads faces per pointer frame.
- `units::Length::from_millimetres_f64` was added so the pointer's millimetre point comes back into
  the document in one place; `ui::void`'s private copy of that rounding was deleted.

## Ruled out

- **Widening `Constructive` to a profile with holes in this task.** It is a schema bump with the
  wire form, the golden, `param::constructive`, the card, the contour edit and every reader of
  `path()` — a task of its own; filed as G5.
- **A hole as a `Boolean` subtraction step** (extrude the outer ring, subtract the hole ring). It is
  representable today but the tool's height is frozen in the step, so dragging the body taller would
  leave a blind hole and the body would stop matching its area.
- **Treating a nested ring as a hole of the set** (not as material). It would make the opening
  unpullable — the one case the entry names — and it contradicts `Contours`' stored invariant that
  every ring encloses material.
- **Hovering any drawing in the scene** (SketchUp's push/pull needs no selection). It needs picking
  to name the drawing under the pointer and a second point rule for a face that is not the selection;
  v1 reads the drawing the cell was pressed on, and the note leaves the refinement to a later entry.
- **A live region update per frame.** ADR 0093 already closed the "write the derived shape into the
  document per frame" road for the extrusion; the atom caches instead.

## Open, for the owner

- Whether the pull should also arm with **no** selection (hover any drawing) — a mode whose target is
  the pointer rather than the selection. Not taken here because it changes what the Extrude cell means.
- Whether a hole-carrying face should be pulled as **several bodies** (one per piece) before G5 lands.
  Refused for now: one click, one body.
## The scene that found the real wall (2026-11-21)

`/home/alx/cross.z3l` holds an intersection object of two rings whose joints miss each other by 4.6,
6.7, 10.1 and 12.4 µm — the storage rounding the document accepts on `2 µm + radius × 1.746e-5`. Both
rings are open to `geom::boolean`, which welds at 1 nm, so `union_regions` answers nothing and the area
partition is empty for every point: that is why the pull did nothing on it. Filed as X103, with a 3 µm
control probe that reproduces it. A union that meets a whole circle is the second wall: `simplify_loop`
merges its four arcs into one 360° arc, and `Contour::assemble` refuses a one-segment ring — filed as
X104.

The hole question this note left open is answered by ADR 0206: a hole stays inside one body, so a face
with a hole waits for G5 and is never pulled as several bodies. The pull target question (the selected
drawing rather than the pointer's) is still the owner's.
