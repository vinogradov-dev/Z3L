# X99 — the base of an armed boolean, and the ink that names it

## What was measured

- The bug, in the code before the change: `SceneFrame::with_selection_highlight` painted the
  selection and only the selection, and a boolean's base is not in it once the tool is clicked —
  `Editor::update_boolean` builds its operands from `selection.ids()` minus `base`, while a plain
  click on the tool (`Selection::pick`, `Pick::Replace`) throws the base out of the selection. The
  base ring was therefore drawn in its own path ink, the operand in the cyan, and nothing said which
  was the frame.
- The frame's outline overlay repeated one constant for every chain
  (`app/src/document.rs`, `SELECTION_OUTLINE` converted once from `SELECTION_LINE_COLOR`), so even a
  chain that carried another colour was widened in the selection cyan.
- The roles already claimed by a hue in the scene: the selection cyan `(0.15, 0.85, 1.0)`, the guide
  and unselected path amber `(226, 187, 109)` / `(104, 68, 11)`, the refusal red, the grid axes red
  and green, the model blue and the scene green in the icon inks.
- The accent lifted off the workspace — `theme::working_copy`'s rule — is ΔE 6.4 from
  `SceneColors::helper` in P1 dark: the "second accent" and the guide ink are one colour there, and
  the guide is drawn as brackets over the same model.

## Decisions

- `SceneColors::boolean_base` is a frame ink, one value per variant: `(242, 115, 168)` dark,
  `(158, 46, 112)` light. Measured against the workspaces 6.33:1 and 5.17:1, against the panels the
  tree row prints it on 5.58:1 and 6.42:1, and 58–93 ΔE from the cyan, the guide ink, the path ink
  and the beech face.
- Rose, because it is the hue no role claims: every neighbouring hue is spoken for (cyan, amber,
  red, green), so a role that must read *beside* a picked shape needs a colour nothing else uses.
- The value is the frame's and the role is the theme's: a chain is drawn by the renderer without a
  `Ui`, so the constant sits beside `SELECTION_LINE_COLOR`, and `theme::boolean_base` reads it as
  chrome ink for the tree row, with `BOOLEAN_BASE_CONTRAST` = 3:1 pinned on both variants of all
  three presets. The same arrangement ADR 0111 gave the guide ink.
- `SceneFrame::with_picks(selected, base)` is the highlight pass: the base takes the base ink
  whether or not it is still picked, every picked shape keeps the selection ink, and
  `with_selection_highlight` is the same call with no base. A body's base is mixed towards the base
  ink at the selection's 35 %, so the two roles differ in hue rather than only in weight.
- The arm is view state the picture follows: `Document::highlighted_base` is compared with the arm in
  `sync_selection`, so arming, re-basing and dropping each re-upload the frame; the base's chain joins
  `selected_chains` even when it left the selection, so the widened overlay draws it; and
  `paint_selection_outline` repeats the ink each chain carries instead of one constant.
- The tree row of the base prints its name in the base ink (`scene_tree::row`), and the armed card
  prints `Message::BooleanBase` = "Base: <name>" under the operation's name (`ToolView::note`,
  `BooleanArm::base_note`). Both are chrome ink, so they take the theme's accessor, not the literal.

## Ruled out

- **The accent lifted off the workspace** (the working-copy rule): ΔE 6.4 from the guide ink in P1
  dark, so a base ring beside an open level's bracket would be one colour. A second lift of the same
  accent separates by value only, and a value gap is what the two rings already fail at.
- **The guide amber itself** (`SceneColors::helper`): it means "the program drew this", and a base
  ring is a document object the person drew.
- **A neutral**, the text ink: reads on everything but says nothing — the task asks for a second
  accent, and a white ring beside a cyan one is a weight, not a role.
- **Reusing the selection cyan at another weight**: the widened overlay is one width, and a dimmer
  cyan on the base would read as the older, de-selected ring — which is the report itself.
- **A per-preset ink derived from the palette's accent**: P2's magenta and P4's violet would collide
  with the action accent the armed ribbon cell already wears, and P1's copper collides with the
  guide; the value would also have had to travel from a `Ui` into the frame's upload path.
