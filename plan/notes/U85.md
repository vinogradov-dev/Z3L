# U85 — the Delete key takes the whole selection, behind one question

## What was measured

- `crates/engine/src/node_cmds.rs` had `node.delete` for one id and no batch. `Session::dispatch`
  snapshots the document once per call (`session.rs` `run`/`record`), so a loop over a selection is
  one undo entry per node — three Ctrl+Z for three rows.
- The tree was the only surface that could build a multi-selection: `scene_tree.rs:375` `select`
  toggles the row on `Ctrl`/`Cmd`/`Shift`, and the viewport's pick always replaces
  (`Editor::select_viewport_hit`). The tree's row menu calls `node.delete` for the row it was opened
  on, so a selected set had no removal path at all.
- `Project::top_most_nodes` (`project/query.rs:71`) already drops unknown ids, repeats and a node
  whose ancestor is listed; `node.group` and the gizmo commit use it. The batch removal can reduce
  the same way instead of growing a second rule.
- The only modal host in the shell was `ConfirmClose` in `apps/furnicraft/src/file_menu.rs`, drawn
  from `close_question` in `main.rs`; `pending_close` was *not* in the frame's `modals` gate, so a
  close question did not own the keys for its frame.
- The palette lists every `CommandSpec`; `params_for` returns a "select a node" reason for anything
  without a builder, so a new id would have shown up as a dead row.

## Decisions

- `node.delete.many` (`{ nodes: [Id] }`) and `Project::remove_nodes`, which reduces to the top-most
  nodes, refuses the root and bumps the revision once: one gesture is one revision and one undo.
  The engine command filters the root out first, so a selection that holds the frame row as well as
  real nodes still removes those nodes (the root is not an object).
- One node deletes at once; two or more ask. The question reuses the window's host, renamed from
  `ConfirmClose`/`CloseAnswer` to `Confirm`/`Answer`, because it now asks about three gestures and a
  name that says "close" would be a lie; the answer performs the gesture the question named
  (`Gesture::{Tab, Quit, Delete}`), with the tab id recorded so the answer acts on the scene it was
  asked in.
- The pending question joined the frame's `modals` gate: a modal owns the keys for its frame, so a
  second Del cannot stack a question, and Escape — read in `Confirm::show` — is the second *Cancel*.
- The lock is checked in the shell before either path (`delete_request` → `Editor::locked_selection`
  then `locked_refusal`), which is the same sentence the tree shows for a locked row. A batch
  command in the palette needed the same whole-selection guard, which also fixed `node.group`
  refusing only the primary — the tree's own guard already refused any locked member.
- `Editor::select_nodes` (public, beside `select_node`) sets a multi-selection up front. The
  `#[cfg(test)]`-only setter in `crates/ui` is invisible to the app crate's tests, so without it the
  two branches (ask, and the batch lock) could only be reached through pointer input.

## Ruled out

- **Looping `node.delete` in the shell.** One undo entry per node, and a mid-loop failure would need
  its own rollback reasoning; the session's clone makes it safe but leaves the history wrong.
- **A second modal type or a second host for the delete question.** Three questions in one host is
  one Escape, one button order and one place to change how a destructive answer reads.
- **Asking about a single node.** Undo covers it and the skill's invariant says a dialog is not the
  answer when undo is; the owner asked for the question on the set, not on every press.
- **A model-level lock.** Locks are session view state (ADR 0065); the command must stay dispatchable
  from a CLI or the assistant, which have no lock flags.
- **Clicking tree rows in the unit tests.** A row publishes no accessibility label, so the frame test
  finds its row by the rectangle the frame drew the name in (`Harness::tree_row`); the pure tests
  build the selection through the editor instead of driving a pointer.
- **Keeping the modal id `scene-confirm-close`.** The surface is not a close any more; the id is
  ephemeral state, so the rename costs nothing.
