# U123 — three panel cells, and what a panel becomes is chosen on the part

## What was measured

- `crates/ui/src/toolbars/spec.rs` (`FURNITURE`, the `furniture.panels` group, 948–1000): five
  cells — post, shelf and wall, each `ToolKind::Fill { class, mode }` with `method: Fill the
  largest fit` and one `*.shape` variant — plus `furniture.panels.void` (`ToolKind::Void`) and
  `furniture.panels.contour` (`ToolKind::PanelContour`). The class is the cell's.
- `spec.rs:165–190`: `FILL_POST_SHAPE`, `FILL_SHELF_SHAPE` and `FILL_WALL_SHAPE` are three
  identical rows differing only in the class, and their ids
  (`furniture.panels.{post,shelf,wall}.shape`) are also workspace pins.
- `crates/ui/src/editor/fill.rs:23–58`: `FillArm { class, fill, mode }`, and `arm_fill` refuses
  without an open product or without the class's `fill` trait. Nothing else chooses the class.
- `crates/engine/src/panel_cmds/fill.rs:38–80`: `panel.fill` already takes `parent`, `at`,
  `class`, `mode`, `free` and `name`, so the class and the mode are parameters a card can supply
  and the command needs no change.
- `crates/engine/src/panel_cmds/panel.rs:40–90`: `panel.create` takes `class: Option<ClassCode>`,
  `outline` and `bevels`; an unclassified board is today's default (ADR 0034).
- `crates/ui/src/class_picker.rs:1–20`: a class is written through `node.property.set` on the
  reserved `class` key; no command knows that a panel's class also chooses its axis pair.
- `crates/model/src/panel/classify.rs` carries `classify_outline` only: the plane→role rule N32
  describes does not exist in the tree, so nothing can be born with the role its plane implies.
- `crates/engine/src/session.rs:620–635`: every command already runs on a copy of the document,
  so a command may measure a state it never publishes.
- `crates/ui/src/inventory.rs:274` binds `probe.void` to `V`; `furniture.panels.void` is a
  separate binding the shell consumes (`app/src/shortcuts.rs:81`, `:155`) for the niche toggle, so
  the cell can leave the ribbon and the atom keep the key.

## Decisions

- **The class belongs to the build, not to the cell.** `ToolKind::Fill` loses its two fields and
  the armed `FillArm` takes the class the creation menu names; one cell then serves post, shelf,
  wall and (from U124) the overlay wall. The build (largest fit or the niche's shape) is a
  property of the part, which is what supersedes ADR 0110's "the build is in the cell".
- **The build is one menu with three kinds of row**: the class, the build and (from U125) the
  count. Before the click the rows are the tool card's (ADR 0119), after it the same rows are the
  node context menu, which needs no card at the pointer because nothing is being drawn.
- **`panel.build.set` measures the void on a copy.** The command takes `panel`, `class` and `mode`,
  clones the document, detaches the target part from that clone, measures `Project::niche` at the
  part's centre — which is inside the void only once the part is gone — and re-plans with
  `fill_plan_in` for the new class's pair and the new mode. It then writes class, outline, bevels
  and placement on the real document in one undo entry, keeping the id, the name and the material.
  No document field and no model change: the void is derivable while the document is in front of
  us, and a stored copy would go stale at the next resize.
- **A retired id is no pin.** `ribbon.pinned_variants` entries naming the retired cells or their
  `.shape` rows load as nothing pinned, which the existing unknown-id fallback already does; the
  setting is dropped on load rather than kept as a dead key.

## Ruled out

- **A per-class cell that only picks the class** (three cells whose click arms the same fill with
  a different class): the owner's ask is one panel cell and the class chosen on the part, and three
  cells would keep today's "name the class before the part" for a maker who already has a void.
- **Storing the section the part was born from on the panel**: a second copy of a measurement the
  niche already answers, and one that a resize (ADR 0026's rule for derived data) would falsify.
- **Re-measuring the niche through the part instead of detaching it**: no sight setting hides a
  part from `Project::niche`, and a board inside the cell is the wall the cell stops at.
## Step 1 measurements: the ribbon map (2026-11-24)

- The map's `furniture.panels` group held five cells, three of them `ToolKind::Fill { class, mode }`
  plus one `.shape` variant each; the class travelled from the cell through `ready` into
  `ToolAction::Fill { class, mode }` and the arm.
- `FillArm` (`crates/ui/src/editor/fill.rs`) already carried the class, the pair and the mode, so the
  cell only ever supplied values the arm re-stated.
- The V key was filed under the retired `furniture.panels.void` row and consumed by
  `app/src/shortcuts.rs`; the atom `probe.void` had the row, the context menu and no key.
- The tests that encoded 0110 were five: the pinned-mode test, the two-builds list, the wall cell, the
  open list's two rows and the armed-mode face.

## Step 1 decisions

- **`ToolKind::Fill` is a unit variant** and `PanelBuild { class, mode }` lives in the editor as view
  state; `RibbonContext::build` carries it to `ready`, which names the build in the hint and answers
  the same `ToolAction::Fill { class, mode }` as before. A press remembers the build for the next
  click and a press on the same build drops the arm.
- **The pressed state answers "a fill owns the next click"**, not "this class": one cell serves all
  three, so comparing the class would leave the cell unpressed while its tool was armed.
- **The `Rectangle` row is in the map and planned.** Cutting a rectangle board needs a drawing intent
  of its own (a ring that becomes a `Rect` outline so the card can still edit its sides); the row
  carries its artwork and its words, and `run` stays `None` until that intent lands, which is why the
  Furniture tab draws two cells and the by-points cell draws nothing.
- **The V key belongs to the atom**, and the niche is armed from the key and from the open product's
  context menu; the ribbon cell, `ToolKind::Void`, `ToolAction::Void` and `ToolActivity::Void` retire
  with it.
## Step 2 measurements: the card at the pointer (2026-11-24)

- The fill's card is not `tool_card::ToolView` built by hand: `Distances::show`
  (`crates/ui/src/distance.rs`) builds one from the two gap rows and draws it through
  `tool_card::show`, so the class and the build had to reach that call.
- The card had two row kinds only — a number (`ToolRow`) and one switch (`ToolToggle`) — so a
  choice among a few words had no atom.

## Step 2 decisions

- **`ToolChoice` is a new atom of the card**: an ordered list of `Message` options and the index in
  force, drawn as chips above the numbers, and `ToolOutcome::pick` answers `ToolPick { row, option }`
  — the row of `ToolView::choices` and the option in it, so the card stays generic and the fill's
  vocabulary stays in the shell. A card of choices alone draws them and no field.
- **The fill's card offers two rows**: the class (post, shelf, wall) and the build (largest
  rectangle, niche shape), in that order, so a pick is an index pair and the shell maps it back
  through `FILL_CLASSES`. A pick re-arms the fill with that class and build in the same frame, so the
  ghost, the pair and the click all follow one value; a class the registry refuses answers with its
  sentence in the status bar and leaves the choice where it was.
- The card's title is the cell's name («Panel»), not the class: the class is now a row of its own,
  and a title repeating it would say the same word twice in a 100 pt plate.
## Step 3 measurements: panel.build.set (2026-11-24, before the first edit)

- A fill command already answers the whole measurement: `panel.fill` runs
  `project.niche(point, Sight::none(), Some(contact))`, then
  `project.fill_plan_in(&niche, parent, FillRequest::new(point, fill, mode, thickness, free), Sight::none())`,
  and the plan carries `nominal_size`, `outline` (`Rect` with corner features or `Contour`),
  `placement` and `bevels`. So the parts the new command needs are all in the tree.
- The gap is the write. `model` has `set_panel_nominal_size` and `set_panel_outline(id, contour)` —
  the second takes a ring and refuses a rectangle panel (`PanelNotContour`). There is no setter for a
  `PanelOutline::Rect` with corner features and end bevels on a panel that already exists, so a class
  that changes the section pair cannot be written today without a new model method.
- `Project::remove_node` exists, so measuring "the void the part sits in" on an inner copy of the
  document is one call and lands nowhere.
- The command must move the part as well as its section: a plan's `placement` is the niche's own,
  so the write covers placement, nominal size, outline, bevels and the class in one revision.

## Step 3 shape to build

1. `model`: `set_panel_shape(id, nominal_size, outline, bevels, placement)` — one revision, the same
   validation `panel.create` applies to a candidate panel (bevels against the outline, the core, the
   machining that stays inside it), and the frame movement `set_panel_outline` already does.
2. `engine`: `panel.build.set { panel, class, mode }` — refuse a node that is not a panel, a class
   with no `fill` trait, and a void that no longer holds the part (the copy with the panel removed
   measures nothing, or `fill_plan_in` refuses); then write through (1) and `settle_revision`.
3. `ui`: the node context menu's rows — the class and the build, the same two choices the card
   draws, dispatching the one command.

Open question for the owner before (1): a class change re-cuts the board in the void it fills, which
a part nobody meant to refit would also lose its outline to. The alternative reading is that the
class alone changes and the outline stays as cut. The entry asks for the re-derivation; the cost is
that a hand-edited outline is replaced by the section.

## The owner's rulings on step 3 (2026-11-24)

- **A created part keeps its role.** There is no class row on the part and no command that writes a
  panel's class after creation, so `panel.build.set` takes the build alone: it re-reads the void the
  part sits in and re-derives the outline for the same class and the other mode. Task entry, ADR 0239
  and the domain guide say so; the class picker in the inspector stays the generic node property it
  always was and this task adds nothing to it.
- **The fit build is called «Rectangle» / “Rectangle”**, not «Наибольший прямоугольник»: the row sits
  beside «По форме ниши» and the long name said the same thing twice.
