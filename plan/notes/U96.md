## What was measured

- Five places spelled a key before this task: `shortcuts.rs` (`consume_key` with a code),
  `crates/ui/src/toolbars.rs` (`shortcut(tool)` and `shortcut_label(tool)`, two matches over the same
  ten tools), `crates/ui/src/toolbars/spec.rs` (a `shortcut` string per cell), `settings.rs`
  (`shortcut_table`, 13 hand-written pairs plus the drawing tools) and `messages.rs` (eight header
  captions carrying `(Ctrl+S)`-style suffixes). The Settings page already printed `Del` where the
  inventory row said `Delete` — the drift was observable, not theoretical.
- 23 keys are bound: 8 shell actions (`file.new`, `file.close`, `file.save`, `edit.undo`,
  `edit.redo`, `palette.open`, `view.panels.hide`, `view.panels.collapse`), `node.delete`,
  `view.layout.maximize`, the three live View cells (`O`, `F`, `G`) and the ten drawing methods.
- A key belongs to a *method*, not a command: `object.path.create` has ten drawing methods with ten
  keys, and the ribbon cell id is the method id. So the key table is keyed by command id, shell
  action id or map method id — the three id spaces the interface already has.
- `egui::Key::name()` spells `S`, `0`, `Delete`, so a label is derivable: `Chord::prefix()` plus the
  name is `Ctrl+Shift+0` and `Shift+R`. The label stays a const field and a test proves it equals the
  derivation, because a `&'static str` cannot be built at compile time in a const table.

## Decisions

- `KEYS` is a const table in `crates/ui/src/inventory.rs`, beside `ROWS`: one `Binding` carries the
  id, the `Chord`, the `egui::Key` and the printed label. `Row` lost its `key` field — a row's key is
  `binding(row.id)`, so the key is still the row's column but written once.
- `ACTIONS` holds the ids the shell runs without an engine command, each with its `Message`; the
  gate refuses an action no key runs and an action id that is also a command.
- The shell asks by id (`consume(input, "file.save")`): a field of `Shortcuts` is an action, never a
  key. `take_drawing_shortcut` keeps its shift-first loop, now over the bindings of `CONTOUR_TOOLS`
  via `spec::method_id`.
- `spec::method_id(tool)` is the inverse of the map's `run` over the ten tools — a const match, so
  the frame path does no map scan; a spec test holds it to the map.
- The grid key (`G`) moved to `take_shortcuts` as `grid_snap`; `Document::toggle_draw_grid` applies it
  only while a draft runs, which is the behaviour the viewport had.
- The header's eight captions lost their `(Ctrl+S)` suffixes and ask `inventory::key_label`, so a
  remap reaches them without a message edit.

## Ruled out

- Keying the table by command id only, as `Row.key` was: `object.path.create` has six live methods
  and ten keys, and the F/O/G cells run view actions no command owns. The method id is what a key
  starts, and the ADR's "key of a method" says the same.
- A second table for methods (a `METHOD_KEYS` beside `ROWS`): two registers is the defect U96 closes,
  and `ATOMS` is the ADR's place for a mechanism, not for a file operation.
- A `const fn` lookup so `ToolSpec` could keep a const `Option<&'static str>` shortcut: `str` equality
  is not const (U94 hit the same wall), so the cell exposes `ToolSpec::key()` at draw time.
- Keeping the Settings page's own `(id, Message)` list and deriving only the label: it already read
  `Del`, and a fifth list with a coverage test is the shape ADR 0117 refuses.
- Failing the gate when a *command* has no key: most commands are reached by a card, not a key, and
  the table is a register of bindings, not of capabilities.
