# Y11 — the camera's lens is the document's, and the render stops choosing one

Y5 landed depth of field and put the aperture and the focus on the render's `Settings`, following the
studio (ADR 0248). The owner's answer: a camera's settings are saved with the camera. This is that
move, and it is the smaller half of Y5: the thin lens, the concentric disc and the circle of confusion
do not change, only where the two numbers live.

## What was measured

- `crates/model/src/camera.rs` had a projection and nothing else; `crates/final/src/job.rs::run` wrote
  the render's lens onto a *copy* of the camera it was handed, which is the shape the studio already
  used. Both were green and both were the wrong home: the same scene file rendered a different picture
  from the window, the line and the assistant.
- The camera card (`crates/ui/src/camera_card.rs`, 4 tests) had one commit path for the projection;
  the lens takes a second token so a focus drag never rewrites a projection beside it.
- The registry grew from 69 commands to 70 (`camera.lens.set`), and the inventory from its last count
  to one more `Card` row in the camera context; both counts are asserted by their own tests.
- The schema moved 34 → 35 and the one golden file now carries `"lens": {"aperture": 45000, "focus":
  2000000}` — 45 mm of radius focused at 2 m, which is the camera Y5's device tests were tuned on.

## Decisions

- **`CameraLens` on the node, validated three times.** The value, the file and the node each refuse a
  radius past 500 mm or a focus with no distance in it, because a document built in memory must not
  hold what the wire refuses. `PINHOLE` is the born state, so a camera saved before this task is a
  camera that renders exactly as it did.
- **One command, `camera.lens.set`.** It is the projection's neighbour and follows its rules: one
  revision, one undo entry, a refusal that writes nothing, and an id that is not a camera answered with
  `CameraNotFound`. A place in the inventory is a `Card` of the camera context, no key and no icon:
  a lens is a field, not a tool.
- **The document's camera is what the Render place renders through.** `main.rs::start_render` now asks
  `scene_build::scene_camera(project, view)`, which is the rule the viewport already follows (an active
  authored camera pins the view), so the place's button and the viewport's picture agree.
- **The render's lens is deleted, not deprecated.** `Settings::with_lens`, the page's two fields, the
  page's aperture cap and `--aperture`/`--focus` are gone. Two homes for one number is the defect this
  task exists to remove, and a fitted view — the one camera a document does not hold — stays a
  pinhole until a maker authors a camera.

## Ruled out

- **Keeping the render setting as an override of the document's.** It reads well ("this image at
  f/16") but it makes the lens a number with a fallback, and a fallback is where a person cannot tell
  which value the picture used. If a workshop asks for it, it is a new record with the precedence
  written down.
- **A lens on the projection enum.** `CameraProjection::Perspective { fov_y }` is what the projection
  *is*; a lens is the camera's, and an orthographic camera carries it too — it simply never reads it,
  exactly as a point light carries a size it does not use.
- **A second schema field only for perspective cameras.** One wire layout for the node, like the
  light's, so a projection switch never loses an edit.
