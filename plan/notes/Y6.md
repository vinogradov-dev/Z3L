# Y6 — What was measured

## What was measured

- `crates/final/src/gpu/mod.rs:259`: the run is a strip loop, and one strip traces every sample
  before the next strip starts; `read_back` (`:338`) runs once per strip after that strip's whole
  sample loop, so no partial picture exists anywhere until the run ends.
- `crates/final/src/gpu/mod.rs:386`: `Progress` carries a total, a done counter and a cancel flag,
  and nothing else — no pixels cross the thread boundary today.
- `crates/ui/src/render_page.rs:203`: the page is handed `scene`, `settings`, `bounds` and `stage`;
  `Stage::Done` (`:180`) carries `{path, width, height, samples}`, so the largest thing the place can
  draw is a path.
- `app/src/render_place.rs:126`: the run is one thread over a cloned frame, and `take_finished` polls
  `is_finished` — a frame-boundary answer, which is the pattern a snapshot would reuse.
- `app/src/document.rs:259`: the shell already registers a wgpu colour view as an egui texture and
  updates it on resize, which is the route ADR 0211 named for the preview.
- `crates/final/src/image.rs:52,94`: `from_accumulation` divides by the sample count and
  `to_rgba8(exposure)` tone-maps, so a preview reuses both and the exposure stays one curve for the
  picture and for the file.

## Decisions

- V-Ray and Blender are references a session looks at, never specifications it copies (owner,
  2026-11-21): the render grows step by step toward a product a workshop can use, and this entry is
  one step of that, not a parity programme. Every borrowed behaviour is decomposed into the button,
  the feedback, the cancel and the awkward case, and decided in our words (AGENTS §1.3, §4.6).
- Refinement is sample-major over the whole frame rather than strip-major: a picture that arrives
  whole and cleans up is what a person reads as progress, while a top-down fill reads as a machine
  doing pieces. The price is holding the device accumulators for the whole run — up to 256 MB at the
  pixel cap.
- The preview leaves the device display-sized and bounded, 1024 on the longer side, and is
  tone-mapped on the CPU by the file's own curve, so dragging the exposure re-tones the last picture
  without a run.

## Ruled out

- Reading the full accumulator back on every checkpoint: 256 MB per checkpoint at the cap, tens of
  times a plate.
- A queue of snapshots: a reader slower than the tracer grows memory without bound, while one
  mailbox slot drops pictures instead.
- Letting `ui` own the texture: `ui` must not see `wgpu`, and ADR 0211 already named the shell as
  its owner.
- A second renderer for the preview, a low-sample viewport pass: two pictures of one scene drift
  apart, and the preview would stop showing what the plate will be.
## What the session that built it found

- **The accumulator is 64 bytes a pixel, not sixteen.** `layout::GpuPixel` is four `vec4`s — the sums,
  the second moment, the albedo-and-distance guide and the shading normal — so a 2480 × 3508 plate
  holds 8 699 840 × 64 B ≈ 530 MiB on the device for the whole run, and a request at the 16 Mpix cap
  holds ≈ 976 MiB. The note above estimated 256 MB from the sums alone; the bands were kept at
  `MAX_STRIP_PIXELS` (a million pixels, 64 MB a buffer) for that reason, and the cap is still a
  refusal by name rather than an allocation the driver discovers.
- **Bands own whole snapshot blocks.** A snapshot pixel is a block of image pixels, and a band is a
  run of image rows; if a band's rows end inside a block, that block is the average of part of two
  bands and the reduce pass of each would overwrite the other. `SnapshotShape::of` picks the stride
  (a power of two, 1024 on the longer side) and `Tracer::accumulate` rounds every band's rows up to
  whole blocks, so `gpu/reduce.wgsl` can run band by band into one picture buffer.
- **The filter's pad rows are read, not traced twice.** `read_rows` copies a band's own rows plus the
  `pad_rows()` the filter's widest tap reaches into out of the neighbouring band's accumulator, so the
  denoised image keeps the seam-free bands the strip-era code bought by tracing the pad twice.
- **A checkpoint is two rules, not one.** A quarter of a second (`SNAPSHOT_INTERVAL`) makes a plate
  publish about four times a second; eight evenly spaced sample counts (`MIN_CHECKPOINTS`) make a draft
  that finishes in 60 ms publish a handful instead of nothing. The last sample is never a checkpoint —
  the finished image follows it with the same count.
- **A snapshot carries radiance, not `Vec<u8>`.** The entry sketched
  `Snapshot { width, height, samples, pixels: Vec<u8> }` and then asked for the shell to tone-map it;
  bytes cannot be re-toned, so `Snapshot` carries an `Image` (linear radiance at display size) and the
  shell applies `Image::to_rgba8(exposure)` — the file's own curve. The finished image is published
  after the PNG is on disk, from the same `Image` that was encoded, so the last picture is the file to
  the code value (a device test asserts it byte for byte).
- **The picture is an egui texture the shell owns** (`Rgba8Unorm`, `register_native_texture`, the
  viewport's own contract), written with `queue.write_texture`; the size change re-registers, the
  exposure does not. `theme::picture(ui)` is the no-tint ink a feature module may not name itself.
