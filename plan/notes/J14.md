# J14 — what the wire, the key and the consent cost, measured before the first edit

what the wire, the key and the consent cost, measured before the first edit

## What was measured

- **The dependency graph already resolves, offline, on the system OpenSSL.** `ureq 3.5.2` with
  `default-features = false, features = ["json", "native-tls"]` pulls `native-tls 0.2.18` →
  `openssl 0.10.82` → `openssl-sys 0.9.118`, and `cargo metadata`'s resolve nodes carry
  `openssl-sys` with an empty feature list — `vendored` is off, so the tree links the system
  `libssl` (pkg-config answers 4.1.0 here). `rustls` and its C provider stay out entirely.
- **`ureq` feature names differ from 2.x**: `native-tls`, `native-tls-no-default`,
  `native-tls-webpki-roots`, `json`, and the `vendored` switch that would hand `openssl-sys` its
  vendored build. The gate can read the resolved feature set from
  `cargo metadata` › `resolve.nodes[].features`, which is a real check and not a comment.
- **The turn already has the shape the wire needs**: `ChatBackend::ask` returns at once and `take`
  hands the answer over a frame later, so a worker thread satisfies it with no change to `Turn`,
  and `Reply { text, calls, checklist, lines, more }` carries exactly what one completion returns.
- **A chat batch is `Vec<BatchStep>`** (`Turn::advance`'s `dispatch` closure), so the wire's acting
  tool is one `command_batch` whose steps become that list. `mcp::tools::StepRequest` already
  derives `schemars`, so the schema a model reads is the struct the parser accepts.
- **`engine::guide()` is the system message** (it is already what `command_list` answers with), and
  `CommandRegistry::specs()` gives id + label rows: a compact catalogue without the 40 151-token
  answer J15 shrinks.
- **The shell's hook is `App::apply_agent`** (once per frame, `Program::parse` of the settings'
  command) and `App::send_chat`. `AssistantSettings` is `#[serde(default)]`, so new fields load
  from an older `settings.json` without a version bump; `SettingsStore::folder()` is the directory
  the key file sits in.
- **The turn's fixture** is `crates/mcp/src/chat.rs`'s `session()` — a product plus one panel to
  rename — and `drive()` runs a whole turn at frame boundaries; a stub HTTP server can be a
  `TcpListener` on port 0 in the same test.

## Decisions

- **The transport is one blocking client in `mcp`, on the operating system's TLS**, and the request
  runs on a worker thread whose answer lands in an `mpsc` channel — `ask` never blocks a frame.
- **The gate counts the exception instead of hiding it.** `openssl-sys` leaves
  `C_VENDORING_CRATES` and becomes a checked row: the resolved graph must not enable its `vendored`
  feature, and the sentence names what to turn off. Every other C-vendoring crate stays banned.
- **The wire's `command_batch` is narrower than the server's**: `steps` only. `dry_run` is the
  session mode's (ADR 0190), `save` is the person's own *Save*, and the product is the window's
  open one — none of the three may be a cloud model's choice.
- **Two backends, one precedence**: an agent process the workspace names owns the model loop
  (ADR 0230); the OpenAI endpoint is the backend when no process is configured. A settings hint
  says so.
- **Consent is workspace state, per endpoint**: `AssistantSettings.consent: Vec<String>`, drawn by
  the panel before the first message to an endpoint it does not hold, and cleared on the settings
  page. The card names what actually leaves — the conversation and the program's own description —
  rather than the "scene digest" ADR 0189 guessed at, because nothing sends a digest.
- **The key has two homes and one reader**: `Z3L_AGENT_KEY`, then `agent-key` in the settings
  folder with no group or other bits (`0600`), read by `mcp::openai`; a file anyone can read is
  refused with a sentence, not silently used. It never enters `Debug`, a log line, a refusal or
  `settings.json`.

## Ruled out

- **Exposing `command_list`/`query` as chat tools.** The turn dispatches batches and nothing else;
  a read tool would be a second dispatch path inside the backend, and the guide plus the catalogue
  in the system message answer the ids without it.
- **Streaming (`stream: true`) now.** `Reply::part` exists for it, but SSE over the same client is
  its own change with its own tests; one completion per call is what the Done clauses need.
- **A network test.** Every test binds `127.0.0.1:0` and speaks plain HTTP to a stub; nothing
  reaches a provider and no key is needed.
## What landed

- The key is read when a message is sent, not when the backend is installed: `OpenAi::ask` reads
  `Z3L_AGENT_KEY`, else `agent-key`, so no frame touches the file and a key written while the window
  runs is picked up by the next message. `Endpoint` therefore holds no key at all.
- The wire's `command_batch` takes `steps` alone. `dry_run` is the session's mode, `save` is the
  person's own *Save*, and the product is the window's open one, so a cloud model chooses none of the
  three — which is why the wire's request type is narrower than the served tool's.
- Both vendoring rules now read the whole resolved graph: a workspace member is never one of those
  crates, so the old check could not fail. `openssl-sys` passes while `vendored` is off and the gate
  fails the moment it is on, proved by flipping the feature for one run.
- The stub endpoint and the wire-shaped answer live in `testkit`, so the wire's own test and the
  window's consent test drive one client and one answer instead of two copies.
- The map row and the debt entry were written from the primary, where `plan/` has its writer; the
  map can only name `crates/mcp/src/openai.rs` once the merge put the file on `dev`.
- P27 was filed on the way: `cargo xtask file plan/map.md` validated against the map on disk, so a
  row naming a path that did not exist yet was written and then blocked every verb behind it.
