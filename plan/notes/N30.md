# N30 — What was measured

## What was measured

The entry claims the command stores a splitting cutout and the panel then stops drawing. The tree
does not: the refusal is already there, and it was measured, not read.

- `crates/model/src/project/panel_cmds.rs:755` `validate_machining_entry` builds the panel geometry,
  takes the candidate region for a through cutout and calls `validate_core`
  (`:832`), which runs `core_violation_of` (`crates/model/src/panel/machining.rs:456`) on the exact
  2D subtraction of `PanelGeometry::core_region()` minus every through cutout, and answers
  `ProjectError::CutoutSplitsCore { panel }` when more than one piece is left. `Project::add_machining`
  and `Project::update_machining` both validate **before** the revision moves and before an id is
  consumed; `panel.machining.add`/`update` dispatch straight into them.
- Measured with a probe test, since deleted: on the sample 700 x 500 shelf, the strip
  `x 0..700, y 200..250` through is refused by `panel.machining.add` with
  `Model(CutoutSplitsCore { panel: Id(2) })`, with `revision` still 0 and `can_undo()` false; the same
  strip on an existing blind record is refused by `panel.machining.update` with the same error, the
  revision untouched. `ProjectError`'s sentence is "cutout on panel {panel} would split the core
  into disconnected pieces", so it names the panel and the split.
- The whole-core case is `CutoutRemovesCore` ("would remove the whole core"); there are two variants,
  not one.
- The model tests already cover the rule at the `Project::add_cutout` level
  (`crates/model/src/project/panel_cmds.rs:1128` `cutouts_that_split_or_empty_the_core_are_rejected`,
  `panel_resize_validates_existing_cutouts`), and the core trace itself in
  `crates/model/src/panel/machining.rs:640-667`. The UI door is covered: the contour editor's
  `apply` is refused and keeps the draft (`crates/ui/src/contour_edit.rs:663`
  `a_cutout_ring_that_leaves_the_core_is_refused`).
- **No engine-level test** names either refusal through `panel.machining.add`/`update`, and no test
  covers the case the entry calls "a material that reaches only part of the width": a panel whose
  core is narrower than the cutout's span, where the cutout trims the far end instead of splitting
  and must be accepted.
- The entry's Why cites `PanelPlan::fold` answering `CoreNotOneRegion`. That path cannot be
  reached by a cutout: `CompileMachining::compile` (`crates/param/src/machining.rs:104`) turns a
  cutout into `OpEffect::Subtract`, a post-extrusion boolean step; `OpEffect::CutRegion` — the only
  producer of that error — has no producer left in the tree.

## Ruled out

- Rewriting the check: the rule the owner stated is exactly what `core_violation_of` does, and the
  probe shows it running before the document changes.
- Adding a second `CoreViolation` variant for the UI: the card reads `PanelDiagnosticCoreDisconnected`
  for a loaded file, and the command's own sentence for a chosen cutout, which is the split the
  entry asks for.
## What landed

The rule already held; the entry closes on the coverage that pins it, with no behaviour change.

- `crates/engine/src/session.rs`: `a_cutout_that_splits_the_core_is_refused_without_mutation` (the
  command spec is disabled for the strip, the refusal carries the panel, the sentence names the
  split, the revision stays at zero, no undo entry, no record), `an_update_into_a_splitting_cutout_is
  _refused_without_mutation` (a blind strip turned through is refused, the stored depth is kept and
  one undo still takes the add back), `a_cutout_that_trims_a_narrow_core_is_accepted` (a 700 x 220 mm
  contour panel whose material reaches only part of the strip's width), and
  `a_cutout_that_removes_the_whole_core_is_refused` (the other sentence).
- `crates/project/tests/scene_file.rs`: the golden's shelf is asserted to keep its blind cutout,
  which the through-cutout rule never touches.
- Two sentences stay: `CutoutRemovesCore` and `CutoutSplitsCore` say different things about what is
  left, and the card shows whichever the command answered.
