# J5 — the editor as a tool server, and what the protocol needed from the tree

## What was measured

- `crates/mcp` did not exist; `rmcp` 3.11.0 and `tokio` 1.54 were in no manifest, `schemars` 1.2.3
  already was (J2 put it in `engine`). No crate outside the process could reach a command except
  the command line's four subcommands (ADRs 0183, 0185).
- `rmcp` with `default-features = false` and `server` + `transport-io` is Apache-2.0, pure Rust, and
  needs no C source; its one build script looks for `.githooks` beside the registry copy and does
  nothing. `schemars` 1.0 is its requirement, so the 1.2.3 in the tree satisfies both.
- The `#[tool_router]` macros would have pulled `rmcp-macros` and `pastey` and a generated routing
  layer for four tools whose schemas we already own. `ServerHandler::list_tools`/`call_tool` are two
  methods with a `std::future::ready` inside, so the crate writes them out.
- `ServerHandler: Send + Sync + 'static` (`rmcp` without the `local` feature), and `Session` was not
  `Send`: it holds `Arc<dyn Contact>` and `geom::Contact` was `fmt::Debug` only. The port was the one
  line to change — every adapter (`contact-parry::Parry`, `engine::NoContact`, `geom`'s test stub)
  is a unit value, so `Send + Sync` costs no implementation anything.
- `Session::batch` reports what a batch did (`effect`, `steps`, `refusal`, the three id lists) and
  nothing about files; `z3l run` writes the scene itself. The server therefore needs a writer port,
  not a path.
- `CommandSpec::enabled(session, params) -> bool` takes the parameters, and `command_list` has no
  request per row: 63 predicates, most of which read the parameters and answer `false` for a
  malformed one. `Creation` is already declared by the two furniture creators, and
  `class_rules::allow_creation` already splits "no product open" from "the target is closed".

## Decisions

- The crate is a protocol adapter with two ports: `SceneSink::save(&Project)` (implemented in `app`
  with `SceneFile`, so the preserved sections and the atomic write stay where they belong) and the
  session handed in as an `Arc<Mutex<Session>>`, which is also the handle a test reads the history
  through and the shape J6's local channel will need.
- `geom::Contact` is `Send + Sync`, so a session may be served from a thread that did not build it.
  That is the whole reason the trait grew the bound; the adapters are stateless values.
- `CommandSpec::unavailable(session) -> Option<CreationRefusal>` is the session's half of `enabled`,
  derived from the `Creation` a command already declares rather than a second predicate per command.
  `class_rules::open_product` is that half, and `allow_creation` now calls it, so the sentence a
  listing prints (`Create a product first.`) is the one the command's own refusal carries. The
  parameter half stays where the parameters are: `command_run`/`command_batch` answer with the
  command's own `CommandError`.
- `command_run` is literally `BatchRequest` with one step, so the two tools cannot disagree about
  what an undo entry is. `atomic` defaults to true and `dry_run` to false; both are the engine's own
  switches (ADR 0198).
- `command_batch` refuses an empty list, echoes the parameters of each step so two identical ids stay
  distinguishable, and reports `write: nothing|written|no_file|failed` beside `written: bool`. A
  landed batch whose write failed is a failed call: the next client must not believe the file.
- A refusal is `CallToolResult::error` with the report inside, never a protocol error, so a model
  sees what did and did not land (ADR 0185). An unknown tool name and an unreadable argument object
  are protocol errors, because no tool ran.
- `z3l mcp serve [<scene.z3l>] [--product <node>]` prints nothing on either stream: stdout is the
  protocol's, and the log sink already writes stderr. `--product` is the same flag `z3l run` has,
  for the same reason — opening a product is session state and not a command (ADR 0029).
- The runtime is built in `mcp` (`serve_stdio`), not in `app`: the layer table keeps `rmcp` and
  `tokio` to one crate, and the shell never learns the protocol's name.
- `CommandSpec::creation_word` replaces the CLI's local `level_word`, so the two discovery surfaces
  print one word for one level.

## Ruled out

- **A per-conjunct reason on all 63 predicates.** It would give a `command_list` row a sentence only
  when a request is supplied, and the list has no request: every row would have said "the parameters
  do not match", which is noise a model cannot act on. The session's half is the answer the list can
  honestly give; the parameter half is the run's own refusal. If a later door needs the full reading,
  the seam is `CommandSpec::unavailable` and the enum beside it.
- **A `LocalSet` and `rmcp`'s `local` feature** to avoid `Session: Send`: it would have made the one
  protocol crate's futures non-`Send` for every future caller, and the bound cost three unit values.
- **`#[tool_router]`**: a proc-macro crate for four hand-written tools, and the routing would have
  hidden the one place a tool name becomes a dispatch.
- **A file path inside `mcp`.** ADR 0185 refuses a filesystem surface, and the scene envelope's
  sections belong to `project` and `app`.
- **Enabling the read-only plan phase here.** ADR 0185 puts the gate in the dispatcher, and the phase
  is the chat's mode (ADR 0187, ADR 0190): J7 and J9 own it. This door dispatches what it is asked.
- **A report on stdout.** `z3l export`/`run`/`query` print theirs; a served session cannot, because
  the stream carries frames.
