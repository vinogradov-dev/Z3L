# W1 — a boolean between two bodies is a feature of the constructive object

## What was measured

- `crates/kernel/src/lib.rs:124` and `crates/param/src/solid.rs`: the port and the plan have
  carried `BooleanOp` and `PlanStep` since ADR 0041, so the geometry was never the gap. The document
  was: `Feature` held one `Extrude`, and `param::build_constructive_mesh` refused a history with
  more than one feature (`UnsupportedConstructive`).
- `crates/model/src/object.rs` `Constructive::extrude` and `crates/model/src/project/mod.rs`
  `scan_tree`: every load-time invariant of a payload lives in the tree walk, so a new reference
  between nodes belongs there too.
- `crates/mesh/src/lib.rs` `object_with`: the cache compared `Payload::Constructive(Constructive)`,
  which is the body's own history and nothing else. A tool is a different node, so that key would
  have returned a stale mesh after every edit to the cutter.
- `crates/engine/src/object_cmds.rs` and `crates/engine/src/commands.rs`: a command's `run` gets the
  project, the directory, the params and the contact adapter — no kernel. `object.collapse` is the
  only command that evaluates geometry, and it does so analytically.
- `truck` panics on some coincident-face booleans (`truck-shapeops`), and `kernel-truck` catches
  them (`crates/kernel-truck/src/lib.rs:152`), so a hostile pair is an error, never a crash.

## Decisions

- The step stores `op` and `tool: Id`, never a copy: the tool is a live reference, so one cutter
  serves several bodies and a body duplicated from another names the same tools (ADR 0197).
- `Project::boolean_tools_of(id, body)` resolves the whole closure with each tool's placement in the
  body's own frame, and it takes the history it is handed so a preview of an *uncommitted* step
  resolves the same way the command will.
- `param::constructive_plan` compiles with a `ToolBodies` resolver and absolute frames: a nested
  tool of a tool lands in the same coordinate space, so no frame composition is needed at all.
- The cache key is `ConstructiveInputs { body, tools }`, the closure sorted by id. A tool that moves
  (placement) or changes (history) re-derives its bodies; an unrelated edit does not.
- A history with one extrusion keeps the analytic backend, so an extrusion-only body still needs no
  kernel and `object.collapse` keeps working exactly as before.
- `node.delete` refuses to remove a node a step names (`BooleanToolInUse`). Removing the steps first
  is two visible edits; cascading would be one silent deletion of a body's history.
- The interaction is the contour boolean's arm with a second operand kind (`BooleanOperand`), one
  Escape path, one overlay and one ✓ in `app/src/document.rs`.

## Ruled out

- **Collapse a boolean body in the command.** It needs the kernel and `CommandSpec::run` has none;
  adding one is a new session seam and an ADR of its own. `object.collapse` keeps refusing a history
  it cannot build exactly; the gap is filed in `plan/debt.md`.
- **A second armed mode beside `BooleanArm`.** The Escape order, the overlay and the card would each
  have grown a branch; the kind is one field instead.
- **Three commands, one per operation** (as the contour booleans have). The task names
  `object.boolean.set` with an `op` parameter, and one command keeps the three cells' hints and the
  palette to one row.
- **Validating the tool graph only at evaluation.** A file that cannot be built must not load, and
  the error has to name the object and the tool; `scan_tree` already has both.
