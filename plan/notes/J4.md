# J4 — a batch is one operation, and a copy is how it plans

## What was measured

- `app/src/cli/recipe.rs` held the whole promise: `dispatch()` looped `Session::dispatch_in` between
  `begin_edit` and `end_edit`, and `perform()` wrote the scene once, only after every line succeeded.
  Nothing about a list of commands existed in `engine`, and `crates/mcp` does not exist yet (J5).
- The "all or nothing" the CLI keeps is the shell's: a failed run drops its session. `Session::cancel_edit`
  restores the content of a failed edit, but it goes through `Project::restore_from`, which advances the
  revision on purpose (`crates/model/src/project/mod.rs`), so inside a window "untouched" would have
  been a claim about the content only.
- `CommandOutcome` already reported the created node id and the created machining id and is `Copy`;
  `CommandError` was `Debug + PartialEq + Eq` but not `Clone`, so a report could not hold a refusal.
- `Project::query(&NodeQuery::any())` (`crates/model/src/project/query.rs`) walks every node below the
  root in tree order, so the diff needed no new walker.
- A container's value carries its `children` (`crates/model/src/container.rs`), so `Node` equality marks
  every ancestor of a created node changed: a panel created under a product reported the product too.
  That is why `Container::same_node` exists.

## Decisions

- `crates/engine/src/batch.rs` holds the values (`BatchStep`, `BatchOptions`, `BatchEffect`,
  `StepOutcome`, `StepReport`, `BatchReport`), the diff (`changes`) and one `pub(crate) fn run`.
  `Session::batch` itself lives in `session.rs`, because the history fields are private to that module
  and a batch's only write is installing the copy.
- `Session::trial` copies the document, the saved marker and the open product and shares the directory
  and contact `Arc`s; `Session::land` installs the copy as one undo entry, only when the effect landed
  and the content differs.
- `atomic` and `dry_run` are two switches on `BatchOptions`; the CLI keeps `atomic: true` and passes
  `dry_run` from `--dry-run`, and `.atomic(false)` is there for the tool in J5.
- The report's lists are ids read from the two documents' own walks, with `content_changed` for a
  change no id names (the active camera). `BatchEffect` describes the document, not the mechanism:
  `RolledBack` means nothing of the batch is in it.
- `CommandError` derives `Clone` so a report can hand a refusal to a door.
- `land` closes an open edit scope, so a batch never merges into a drag that was already running:
  the entry the drag pushed is not the one the batch belongs to, and one undo must not take both.
- The CLI keeps the recipe's own line numbers: the report numbers steps, the door maps the number back
  to the file line, so blank lines still number the output the way the file reads.

## Ruled out

- **Undo-based rollback** (`cancel_edit` after a refusal): the content returns and the revision moves,
  and a plan that shifts the revision has touched the document.
- **A second step type in the CLI**: the two doors must call one function, so the CLI builds
  `BatchStep`s from its line-numbered lines.
- **`StepOutcome::Applied`**: in a dry run and in a rolled-back batch the command ran and the document
  did not change; `Ran` says exactly that and `BatchEffect` says whether it landed.
- **Comparing containers by value** in the diff: a created panel would report every ancestor as changed.
- **A `serde` derive on the report now**: `CommandOutcome` and `CommandError` are engine values, and a
  tool's wire form is J5's decision (ADR 0197 records this).
- **An `--allow-partial` flag on `z3l run`**: no recipe has needed one, and ADR 0183 calls a
  half-applied recipe a scene nobody asked for.
