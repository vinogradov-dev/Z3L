# U87 — the transform mode can be off, and Select is the state a window opens in

## What was measured

- `app/src/main.rs` held `TransformMode` with two variants, `Move` and `Rotate`, and
  `Shell::default()` set `Move`, so a window always drew one of the two gizmos.
- `app/src/document.rs` matched the mode four times in `viewport`: the update gate, the
  "did a handle take this press" flag, the move-distance readout and the paint branch. Nothing in
  the tree could express "no gizmo".
- `app/src/status_bar.rs` drew the mode as two `selectable_value` cells after a dim
  *Gizmo* caption; `crates/text` had `Move` and `Rotate` and no word for the third state.
- The task's `Shape` says "the ribbon's two cells stay pressed only while the matching mode is on".
  That sentence is stale: U76 left the ribbon holding tools only, and the mode has lived in the
  status bar since then. `rg 'Message::Move'` finds exactly one drawing site, the status bar.

## Decisions

- `TransformMode::transform() -> Option<Transform>` is the one place that says which states own a
  gizmo. Four matches became one total mapping, and `Select` cannot drift between the drawing, the
  hit test and the consumed-click flag, which are three readers of the same answer.
- `Select` draws nothing rather than drawing handles that refuse the press. An unarmed handle and a
  broken handle look the same to the person, and only one of them is honest.
- The three states are one control in one band (`transform_mode_ui`): three `selectable_value` cells
  with the band's item spacing at zero inside a `theme::control` frame. The shared widget and the
  theme's own selection visuals are reused rather than a hand-drawn segmented control, and the
  hover, press and disabled states stay the theme's (ADR 0063).
- The *Gizmo* caption stays. It names the control in one word the bar already carried, and the three
  captions next to it name the states; removing it would be a second change to the same row.
- The mode stays `Shell` state: no `.fcs` field, no undo entry, no revision — the test asserts that
  a press on the control moves no revision.

## Ruled out

- **A keyboard shortcut for the modes (W/E/R or 1/2/3).** The drawing tools already take letters,
  `ui::toolbars` owns the ribbon's keys, and a mode key would be a second way to one
  state. Not part of this task; it needs its own decision.
- **Drawing dimmed handles in `Select`.** A dimmed handle invites a press and then does nothing,
  which is the worst of the three readings; the mode is either armed or it is not.
- **Keeping the update running and discarding the commit.** The gizmo would still set
  `consumed_click`, so a press near the pivot would stop selecting: exactly the complaint the task
  starts from.
- **A per-tab mode.** The mode belongs to the hand, not to the scene: a tab switch would change the
  tool under the pointer (ADR 0029).
- **A setting for "open in Move".** The owner asked for the break and it is recorded in ADR 0113;
  a default nobody can predict is worse than one the status bar shows.

## The check by eye

`cargo test -p furnicraft --bin furnicraft -- --ignored the_interface_renders_offscreen_to_one_png_per_cell`
renders the whole window offscreen; the status bar was read in
`target/ui-shots/graphite_copper-dark-opacity100-expanded-scale100.png` and the light variant of the
same cell. The band and the accent-filled *Select* cell read as one control in both variants, and the
viewport draws no arrows in the fresh window.
