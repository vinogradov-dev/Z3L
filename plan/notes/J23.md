# J23 — What was measured

## What was measured

- The panel answered `answered HTTP 400` for `https://opencode.ai/inference/go/openai/v1`; the
  owner's curl to the same path worked. The difference is one header: the curl sends
  `x-opencode-session`, the client sent none.
- With a fake key the endpoint answers, without the header,
  `400 {"type":"error","error":{"type":"MissingSessionID","message":"Request is missing
  x-opencode-session and cannot be routed efficiently."}}`; with the header it answers `401
  {"error":{"type":"authentication_error","message":"Invalid credential"}}`. The routing check is
  before the credential check, so the header is the missing piece.
- The client discarded the body: `complete` mapped `Error::StatusCode(400)` to one sentence, so the
  provider's `MissingSessionID` never reached the panel.

## What was decided

- The header is workspace data: `AssistantSettings::headers` is one `Name: value` per line, sent on
  every completion by `OpenAi::with_headers`. No provider name or port is in the code; a gateway that
  needs a session header uses the same field a local server ignores (ADR 0189).
- `Authorization` is refused in that field: the key has two homes (`Z3L_AGENT_KEY`, `agent-key`) and
  the settings file is copied between machines. The hint says the same, and the field is for routing
  and session headers, not secrets.
- A non-2xx response is read before it becomes a sentence: `http_status_as_error(false)`, a 4 KiB
  body limit, `error.message` or `message`, whitespace folded and 300 characters capped. The refusal
  names the endpoint, the status and the provider's sentence, never the key.
- The testkit stub now keeps the headers it read and can answer a status, so both the header and the
  refusal have a test without a network.

## What was ruled out

- Hardcoding `x-opencode-session`, or adding a per-provider table: ADR 0189 says no provider name in
  a type, a match arm or a default, and one data field serves every gateway.
- Generating a session id in the client: the value is the person's, the gateway may tie it to an
  account, and a hidden generated value would be a second identity nobody can read.
- A proxy or an editing of the URL: the gateway checks a header, not a path or a query.
- Putting the header in `agent-key`: that file holds the key and is read as `Authorization`; the two
  are different things.

## The owner's workspace

`~/.config/z3l/settings.json` now names the `go` address and
`headers = "x-opencode-session: ses_test_1"`, the value the working curl used. The old build ignores
the field; the merged build reads it.
