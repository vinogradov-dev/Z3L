# T9 — the class list follows what a shop builds, not the order of the digits

the class list follows what a shop builds, not the order of the digits

## What was measured

- The offered order was the order of `REGISTRY` in `crates/model/src/class.rs`, which is ascending by
  code because `ClassCode::row` binary-searches it. So a person met `10.01` chair, `10.02` stool and
  then `30.01` cabinet, and the placeholder `80.01` came last.
- Two surfaces read that order: the picker's tree (`visible_rows` in `crates/ui/src/class_picker.rs`)
  and the product card's list (`product_rows`), which filters `level = Product` and draws the same
  sequence flat. Both walked `model::registry()`.

## Decisions

- The order is presentation, not identity: `presentation_rank(code)` maps a code to the rank of its
  family, and one private `PRESENTATION_ORDER` constant in `model` states the sequence once —
  `80` general, `30` storage, `70` boards and trim, `40` surfaces, `20` lying, `50` fittings,
  `60` appliances, `10` seating. The registry table stays ascending by code and its test still
  proves it.
- The order is the order of the work: the placeholder is what a new product card carries, storage is
  the case a cabinet shop builds and `70` is the trim that goes with it, then the products it makes
  less often, then what is bought, and seating last because a chair or a sofa belongs to a scene.
- A family the list does not name ranks one past the last one, so a synthetic row in a test or a
  future heading follows in code order instead of panicking; the unclassified sentinel does the same.
- `docs/domain/classes.md` §7 now lists the family paragraph in that order, and the existing test
  compares the sequence instead of only the count: the document and the constant cannot drift.

## Ruled out

- Renumbering the families so code order is the wanted order: a code is an identity, immortal once
  shipped (ADR 0094), and the digits carry no presentation.
- A `rank` field on `ClassRow`: it would add a column to every row of the documented table and to the
  row-for-row test, and only eight values would ever be written.
- Sorting `REGISTRY` itself: it breaks the binary search `ClassCode::row` depends on.
- Removing seating from the product card, or demoting its `level` to `Component`: that is a trait
  change and a registry decision of its own, not an ordering. Seating still is `level = Product` and
  is offered last.
- An ADR: the ordering is reversible, moves no stored number and the owner asked for the break, so
  the rule lives in the constant's doc comment and in `classes.md`.
