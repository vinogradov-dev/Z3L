# J15 — What was measured

## What was measured

- **The answer, before.** `mcp::listing` mapped every `CommandSpec` to a row carrying `params:
  spec.params_schema()` inline, plus `engine::guide()` under `domain`. Measured on the sample
  session: 66 commands, **189 989 bytes** — about 40 151 tokens, the number the entry quotes.
  Of those, 171 789 bytes were the schemas, 18 062 the guide, and the short rows (id, label,
  family, creates) 4 816, so the envelope is under 200 bytes and 73 bytes buy one command.
- **`params_schema` is a function, not a value.** `CommandSpec` stores `fn() -> Value` and
  `params_schema()` calls it (ADR 0185), so a schema is built only when a surface asks. The list
  was the surface that asked for all sixty-six.
- **The Shape line's verdict half is already retired.** `docs/decisions/0226` (accepted the day
  after this entry was filed) ends with "**`command_list` carries no verdict.** The row is the id,
  the English label, what it creates and the parameter schema"; `CommandSpec::unavailable` no
  longer exists in `crates/engine`, and `crates/mcp/tests/served.rs` asserts the absence of an
  `enabled` column. So "whether it runs here, one sentence of refusal" cannot be a per-row column:
  the only refusal a session owns is its **mode**, and `mode` is already in the answer.
- **Three doors answer the list, not one.** The headless `CommandServer`, the window's channel
  (`Call::List`, answered by `App::answer_channel` and by `z3l mcp serve --attach`) and the tests.
  `Call::List` carried no argument, and the channel's own `intent` parsed `CommandListRequest` and
  threw it away, so a per-id request needed the variant to carry it.

## What was decided

- **One tool, two answers, one shape of the row.** `CommandListRequest` gains `command:
  Option<String>`; without it the answer is the short rows + `domain` + `schema_note`; with it the
  answer is that **one** row carrying `params`, and no guide. A row is short or full, never a third
  thing, and `commands` is always the key — the list holds every id in registry order, and the
  schema of the one id asked for, byte for byte `spec.params_schema()`, which is the value the
  command's own `run` parses (that is the whole of ADR 0185).
- **The session's verdict is `mode_note`.** A plan-mode session answers the same sentence a batch
  and `undo` are refused with, `report::PLAN_NOTE`, once in the list. A build session carries no
  note, because there is nothing to refuse.
- **The budget is a published constant.** `mcp::LIST_BUDGET_BYTES = 32 KiB`: today's answer is
  23 278 bytes (4 816 rows + 18 062 guide + envelope), so the promise leaves room for about a
  hundred and thirty more commands. The number is public so the test reads the promise instead of
  a copy of it.
- **An unknown id is refused, not silently empty.** The sentence is the engine's own words plus
  every id that exists: `unknown command `x`: this build dispatches 66 commands — …`, because the
  caller that asked for one id is about to ask for another.
- **A schema is one id at a time on purpose.** The largest today is `panel.create` at 13 244
  bytes; asking for it is a second call that costs a fifth of what the old list did.
- **The CLI's `z3l commands --json` is untouched.** It is a person's and a recipe author's report,
  and it has no context budget; `crates/mcp` is the surface a model reads.

## What was ruled out

- A second tool `command_schema`: two names for one registry row, against the "coarse and few"
  rule of ADR 0185, and a client that reads `tools/list` learns the argument from the one tool.
- A per-row `refusal`/`enabled` column: refused by ADR 0226, and it would have to invent a verdict
  the engine does not hold.
- Trimming the guide out of the list answer instead of the schemas: the guide is the one thing a
  caller reads before it composes anything (J20, ADR 0215) and it is a fifth of the answer;
  the schemas were four fifths.
- A byte budget counted in tokens: the tests measure bytes, and the ratio is a property of the
  model, not of the tree.
