# X91 — What was measured

## What was measured

- `app/src/file_menu.rs` drew the path in an `egui::TextEdit` and listed up to fifty `.z3l` files
  beside it (`scene_files_near` read the folder on the frame path, capped at 500 entries). The
  owner's report — one Backspace deleting two characters — is a defect of that field, and the field
  existed only because the build had no native dialog.
- `rfd 0.18.0` is the smallest binding that covers all three platforms without our own `unsafe`:
  `default-features = false, features = ["xdg-portal", "wayland"]` turns the GTK backends off, and
  its `build.rs` compiles nothing — it adds the AppKit framework link on macOS and refuses a build
  with no backend chosen.
- On Linux the portal client is rfd's own FFI over `libdbus-1`, opened at run time through a
  `OnceLock`-held library handle, so nothing C is compiled and no `-sys` crate enters the tree.
  `zbus` and `wayland-client` were already there (`accesskit`, `winit`); rfd adds neither an async
  runtime nor a second toolkit.
- The blocking call waits forever: `dbus_connection_send_with_reply_and_block(..., -1, ...)`, so
  `rfd::FileDialog::pick_file()` in a frame would freeze the window for as long as the person browses
  — and a frozen editor is exactly the defect this task replaces.

## Decisions

- **A worker thread, not a blocking call.** `AsyncFileDialog` on a `z3l-file-manager` thread with
  `pollster::block_on` is the one shape that is correct on all three platforms: on macOS rfd
  dispatches the panel to the main thread and completes the future from its completion handler, on
  Windows it runs the common item dialog on a COM thread, and on Linux it holds a private D-Bus
  connection. The answer is taken at the frame boundary beside `take_directory`.
- **The worker wakes the frame** (`Context::request_repaint`). Polling with `request_repaint_after`
  would redraw ten times a second for the whole dialog — 10 % of a measured 1.7–9.5 ms frame for
  nothing.
- **The order is data.** `Order { mode, folder, name, lang }` plus `title()`/`filter()` carries the
  whole request — filtered to `z3l`, started where the document lives, named after it — so a test
  asserts a pick without a window and without a file manager.
- **One pick at a time**: a second *Open* answers `Started::Busy` and asks for nothing.
- **The pick belongs to its tab** (ADR 0081): `App::pick_tab` records the asking tab and the answer
  activates it before the save lands, because the file manager draws its own window and a person can
  activate another tab behind it.
- **A cancel is an answer**: nothing opens, nothing is written, the status bar stays quiet. A picked
  save whose name carries no extension gets `.z3l` appended (`scene_file`), because the dialog
  filters by it but does not add it.

## Ruled out

- **`ashpd` directly.** It covers Linux only; macOS (`NSOpenPanel`) and Windows (the common item
  dialog) would then be our own FFI, which `unsafe_code = "forbid"` refuses.
- **The `gtk3`/`gtk4` backends of rfd.** A second GUI toolkit (AGENTS §2), and a build-time dependency
  on GTK headers.
- **Keeping the modal as a shell around the picker** — the title, the new-tab hint and our *Cancel*.
  X91's Shape allows it, but the system dialog already has its own title, name field and *Cancel*;
  a second frame around one gesture would be one frame too many, and the hint is now the only thing
  lost. The five messages that only that modal drew left `crates/text` with it.
- **A parent window handle.** `rfd::set_parent` exists and is the next refinement; `eframe::Frame`
  would have to be threaded from the frame loop into the picker, through the headless harness that
  has no window handle at all. Filed in `plan/debt.md` with the rest of the picker's gaps.
- **The nearby-scenes list.** The file manager's own browser replaces it; the recent files on Home
  stay, and they are the ones the person returns to.
## What was verified

- Headless, through the real frame (`app/src/frame_tests.rs`): a cancelled pick opens no tab, writes
  nothing and leaves no error; a picked save writes the scene under the extension the next *Open*
  filters for; and an answer taken while another tab is in front lands in the tab that asked. The
  picker itself has five unit tests over the order, the busy rule, the cancel and the extension.
- `cargo xtask ci` is green: fmt, clippy, the workspace tests, and the layers, ui-rules, plan, docs
  and skills gates — `rfd` passes the C-vendoring check because it compiles nothing.
- **Not verified by eye.** The system dialog itself cannot be exercised without a desktop session
  (no display in this one, and a headless test must never open one), so the native path — the portal
  on Linux, the sheet on macOS, the common item dialog on Windows — is compiled and reasoned about,
  not seen. The first live run should check: the dialog appears filtered to `.z3l`, starts in the
  document's folder, a cancel changes nothing, and the window keeps drawing while it is up.
