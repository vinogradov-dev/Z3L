# X108 — the field row guessed its button's width, so the panel widened by itself

the field row guessed its button's width, so the panel widened by itself

## What was measured

- Owner report 2026-11-21, reproduced headlessly in `app/src/frame_tests.rs` only with the
  interface in Russian: a chat panel opened over the sample product, one long transcript line and
  a long unsent message in the field, 100 frames at 1280 × 840. The window rect grew by 9.4 points
  a frame — 429.4, 438.8, 448.2 … 1289.4 points wide — until it filled the screen. The same 100
  frames in English left it at 420 × 458, which is why no test had caught it: the default
  `Language` is English.
- The cause is the field row in `app/src/chat.rs`: the field asked for `available_width - 72.0` and
  the button after it took its natural width. «Отправить» is wider than that guess, so the row was
  9.4 points wider than the panel on every frame. A window follows its content (`Resize`, which
  keeps `desired_size.max(last_content_size)`), so the overflow became the next frame's width,
  which made the row wider again, and the window never shrank back.
- 72 was a guess at the button's width, not a measurement: any language whose Send or Stop label
  is wider than 64 points plus the item spacing had the same ratchet, in either mode and whatever
  the conversation held.

## Decisions

- The row is measured from the button outwards: `allocate_ui_with_layout` with a right-to-left
  layout, the button first, the field taking `ui.available_width()` of what is left. No number
  stands in for a label's width, so no translation can widen the panel again.
- The row is given `spacing().interact_size.y` as its height — the height `ui.horizontal` takes,
  which `theme::apply_with` sets — so the panel keeps one row rhythm.
- The regression test asserts the whole rect, not only the width, and runs in both languages: the
  width is what drifted, but a row that moves the height changes what the person sees too.

## Ruled out

- `egui::Sides::shrink_left`, the obvious tool for a field-and-button row: it measures the right
  side first, but it switches to `Extend` while `Ui::is_sizing_pass()` is true, and the first frame
  of an `Area` is always a sizing pass. The field then took the whole row, the panel opened 468.6
  points wide instead of 420, and it stayed there.
- `ui.with_layout(Layout::right_to_left(..))` on its own: the child `Ui` keeps the full available
  height, so the row was as tall as the rest of the window, and the panel grew 62 points before it
  pinned itself to the bottom of the screen.
- The content is innocent: long transcript lines, a long typed message, a transcript that grew by
  one line every frame, and a drag that widened the panel to 600 all left the rect fixed once it
  was drawn. A sweep of 8 screen widths × 8 heights × 4 pixel densities found no width drift in
  English in any of the 256 configurations; the only movement was the one-frame height of a
  window's first sizing pass.

## Found, not fixed

- The Stop button is chosen by `busy`, which `App::assistant` fills with `gesture_in_flight()`, not
  by `Chat::is_busy()`. So a person cannot stop a running turn from the panel — the button says
  Send, and pressing it does nothing because `Chat::begin` refuses a second turn — and Stop appears
  only while a piece is carried. The module comment and ADR 0187 ("the stop is between calls") both
  put Stop on the working turn. A second defect in the same row; it needs its own entry.
