# Y7 — a 3D object wears one material of the render's library

The frame painted every panel from one of three placeholder tones, every band from one grey constant
and every object from a debug colour, while `crates/materials` already held the workshop's library and
`crates/scene` already carried a `Surface` and a `Decor` on every drawable (Y3, Y8). This task is the
mapping, and the key it needs.

## What the owner decided, 2026-11-25

> любой 3д объект, любая поверхность должна иметь материал из списка материалов рендера, как в любой
> 3д программе. Касаемо мебельной панели, она ссылается на материал из номенклатуры, в котороый так
> же ссылка на материал рендера. Но сама панель по факту это обычный 3д объект и ему присваивается
> материал рендера, всем его поверхностям

Read back: the render never reads the nomenclature, and the board/band/handle list in the entry is an
example and not three things to find in the document. The render's material is a slot **on the object**,
one record for every surface of it; the catalogue is how a furniture panel's slot comes to be filled.
That removed the blocker this session first proposed (a catalogue reference id, O16) and made the key a
document field of the render's own vocabulary.

## What was measured before the edit

- `app/src/scene_build.rs` `collect_panel`/`collect_object` pushed `PANEL_COLORS[palette % 3]`,
  `EDGE_BAND_COLOR` and `OBJECT_COLOR`, and `Drawable::with_surface`/`with_decor` had no caller.
- Nothing named a render material: `Panel::material()` is a catalogue `ItemId`, `Object` had no
  material, `Node` has no hardware variant (a handle is an `Object` today, not a hardware record).
- `materials::MaterialId` is L2 and `model` is L1, so a document may not depend on it
  (`xtask/src/main.rs`, `check_layers` refuses a dependency on the same or a higher layer).
- `Session::materials()` already carried the library (Y8); `materials::Store::picture` returns the
  library's own `Picture`, not the frame's, so the shell converts; `scene::Decors` allocates the
  `DecorId` per record per library revision; `final::faces_of` takes the frame and nothing else.
- A tab created by `open_tab`/`new_tab`/`empty_tab` did **not** get the library snapshot: only the
  first tab did, and `take_materials` fires on a reload alone. Fixed here, because a second tab would
  otherwise paint placeholders until the shop edited its library.

## Decisions

- `model::MaterialRef` — a non-zero `u32` beside `ItemId`; the shell converts it into
  `materials::MaterialId` in one place. The document never gains the `materials` dependency.
- One slot per surface-bearing node: `Panel::render_material` and `Object::render_material`, both
  optional and written only when named. `Project::set_node_material` sets or clears it, bumps the
  revision once, refuses a container (and the root), a camera and a light.
- All surfaces of a panel wear the panel's record: both faces, the cut edges and every band. That is
  the owner's "всем его поверхностям", and it is why the entry's separate banding colour is not
  implemented as a second slot: a band's own record is O18's composition.
- `FrameMaterials` (in the shell, where the frame is built) resolves a reference against the
  session's `Library` and reads a picture through the workshop's `Store`; `Document` owns the folder
  and one `scene::Decors`, so a record's picture is decoded once and a moved library drops the
  entries (a replaced scan arrives under a new id).
- Quiet answers keep the placeholder: no slot, a reference the library lacks, a record with no base
  (a lacquer alone, until Y9), and a frame built with no folder. A broken picture is the record's
  flat colour plus a log line naming the record and the file — never black.
- The scene schema moved 32 → 33; the golden, the two recipe scenes and the four engine fixtures
  follow it (ADR 0096: before 1.0 the format has no past).

## What landed (8b6c50c)

- `crates/model`: `MaterialRef`, the two slots, the wire field, the project method and the error.
- `app/src/scene_build.rs`: `Paint`, `FrameMaterials` (`paint_of`, `decor_of`), `evaluate_with`;
  `collect_panel` and `collect_object` paint every drawable they push.
- `app/src/document.rs`: the folder and the decor set, the first frame built with them, and
  `evaluate_with` on every rebuild after `decors.follow(library version)`.
- `app/src/main.rs`: the folder reaches every tab, and a new tab takes the active tab's library.
- Nine tests: a striped decor with the record's turn, a rotated board reading the two axes
  differently, a placeholder for no slot and for a missing reference, metal and glass reaching the
  `Surface` of an object, a lacquer with no base and a picture that cannot be read keeping the flat
  colour, two boards sharing one decoded picture, and `final::faces_of` flattening the same colour,
  finish and picture the viewport draws.
- ADR 0245; `plan/map.md` gains the row (the integration session writes it, the stream does not).

## Still open, and for whom

- **Nothing authors a slot in the window.** The model setter is the seam; a `node.material.set`
  command with its inventory row, its undo entry and a card is its own task (the render stream's
  `files:` hint does not reach `crates/engine` or `crates/ui`). Until then the slot is written by the
  scene file, by a fixture and — once O16 lands — by the catalogue bridge in `panel.material.set`.
- **The catalogue bridge is O16's.** A panel's `material` is still only its cut-list and thickness
  row; the one line that copies the record's render material into the panel's slot waits for the
  catalogue to name one. O18 then decides whether the slot follows a changed catalogue record.
- **A band still wears the panel's record**, not its own banding record; O18 composes layers and
  would give the edge its own list.
- **The coat is Y9.** A lacquer record paints nothing today, by decision.
- **The headless render (`z3l render`) has no folder**, so a PNG it writes has flat colours for a
  decor. The command needs a library path, which is its own line in the debt file (Y8 filed the same
  gap from the other side).
- **A missing library record is silent in the inspector.** The frame keeps the placeholder and says
  nothing a person can act on; an inspector finding naming the node and the id is the natural next
  step beside ADR 0191's seven.
- **A device test for the tracer's image** was not added: `final`'s own device tests prove the lobes
  and the decor path, and `final::faces_of` here proves the frame reaches the tracer as the viewport
  drew it. A rendered metal-vs-matte sphere would be the visible confirmation and needs a GPU, which
  the suite has only where the machine has one.
