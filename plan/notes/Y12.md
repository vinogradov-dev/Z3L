# Y12 — The run draws a picture, and the save writes it

The run draws a picture, and the save writes it

## What was measured

- `app/src/render_place.rs` (393 lines): `start` refused with `choose a file to write the image to`
  while `settings.path` was `None`, `Job` carried the path, and `take_finished` read `report.path`
  out of the thread's `Result<Report, String>`. The place kept only the display-sized `Snapshot` in
  `Shown`; the full-resolution `Image` was dropped by `job::run` after being encoded.
- `crates/final/src/job.rs`: `Settings` held `path`, `Report` held the path it wrote, and `run` ended
  with `encode_png` + `write_atomic` + `publish(Snapshot::of(&image))`. That published snapshot was
  the only way a finished picture reached the place.
- `crates/ui/src/render_page.rs`: `Settings.path: Option<PathBuf>` with
  `refusal() -> Some(Message::RenderNeedsPath)`; `Action::Choose`; `Run.path` printed by the status
  row; the `RenderDestination`/`RenderNoPath`/`RenderChoose`/`RenderWrittenTo` messages were the
  words that row owned.
- `app/src/main.rs`: `take_pick` answered `PickMode::Image` by `render_place.set_path`,
  `ask_for_image` built the `Order` from the scene's own name, and the `ui_shots` and `render_place`
  tests set a path before a run.
- `app/src/cli/render.rs`: `Settings::new(request, exposure, &args.out)`, then `run` wrote the file
  and the report's path was printed. `--out` stays: a headless render has nobody to ask.

## Decisions

- `final::run` returns the finished `Image`; `final::Settings` keeps only the request, the exposure,
  the studio and the denoise switch. `Report` disappears: its three numbers are the image's own size
  and the request's sample count, and its path was the destination being removed.
- `final::save(image, exposure, path)` is the one writer of the one file the crate owns, built from
  the existing `encode_png` + `write_atomic`, so no caller composes a second encoder and a second
  save is just another call.
- The place keeps the full-resolution `Image` beside the display-sized `Shown` (12 bytes a pixel: an
  A4 plate is ~100 MB, the crate's `MAX_PIXELS` cap 192 MB). Saving therefore never runs the tracer
  twice, and a save applies the exposure the page shows now, not the one the run started with.
- A save that fails is `Saved::Refused(sentence)` on the page and the kept image stays; a save that
  succeeds is `Saved::Written(path)`. Starting a new run clears it, because a path describes the
  image it was written from.
- The page's Save button is enabled by `has_image` rather than by the stage: a later run that fails
  leaves the earlier image savable while the status row shows the failure.
- `RenderPlace::page_parts` hands the page the numbers, the flag and the last save in one split
  borrow, so the shell neither clones a path per frame nor borrows the place twice.
- The command line writes the returned image itself (`final::save` after `run`), so a headless
  render still needs `--out` and still prints where it landed.
- The status row no longer prints a file: it is the run's line, and the Save row carries the path or
  the refusal.

## Ruled out

- Keeping the path on the page's `Settings` and writing the file inside `run`: that is the shape the
  task removes — a destination chosen before there is a picture.
- Saving from the display-sized snapshot: it is downscaled to `SNAPSHOT_LONG_SIDE`, so a plate would
  be written at 1024 pixels.
- Re-running the tracer at save time: minutes of work to write an image the place already holds.
- A modal save dialog of our own: the system file manager is the one picker (ADR 0182), and the
  existing `PickMode::Image` order already offers the scene's name.
- A new ADR: the record is amended instead, as the entry's Shape asks — ADR 0250 and ADR 0211 say a
  run's output is a picture and where it lands belongs to the save.
