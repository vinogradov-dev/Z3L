# U94 — One table of places, and the numbers that make the gate worth writing

## What was measured

- Command ids: 56 `pub const *_ID` in `crates/engine/src` (plus `missing.command`, the
  registry's refusal placeholder). Three are named nowhere in `crates/ui` or
  `apps/furnicraft/src`: `CONTOUR_CREATE_ID`, `NODE_ORIGIN_REBASE_ID`,
  `NODE_PROPERTY_SET_MANY_ID`. They are reachable only from the palette by name, and the
  palette cannot build their parameters.
- Ribbon map (`crates/ui/src/toolbars/spec.rs`): 5 tabs, 24 groups, 29 rows with
  `run: Some(…)` and 17 with `run: None,`, plus 62 rows built by `planned(…)`. Icon and run
  are paired one to one (29 `icon: Some(…)`, 17 `icon: None,`), so no live row is missing its
  art today — but nothing but a convention makes that true, and the type allows the opposite.
- Icons: `icons.rs` embeds every file with `include_bytes!`, so a missing SVG is a compile
  error, and a test reads `assets/README.md` to compare the table with the tree. The gap is
  not the file but the meaning: two unrelated actions can share one drawing and nothing
  reports it.
- Palette (`crates/ui/src/palette.rs`): `specs()` lists every command, `params_for(id)` builds
  parameters for twelve of them and answers `PaletteNeedsSelection` for the rest. A row in the
  palette is therefore not a place: it is a name search over commands that mostly refuse.
- Existing atoms, unnamed: one probe serves the niche, the exact distances and the move
  (ADR 0103); one box editor serves the cuboid and the product envelope (ADR 0101); one snap
  resolver serves every drawing tool (ADR 0051). `fill_gizmo` is the only consumer of the
  niche, and it computes the cell itself.
- No table, no check: `cargo xtask ui-rules` reads colours and hosts, `layers` reads crates,
  `plan` reads the plan — nothing compares the registry with the surfaces.

## Decisions

- The inventory is one const table keyed by id, and the gate fails a command with no row
  (ADR 0117). The key is a column, so remapping is data (U96).
- Icon and message are part of a place: a row without either is planned and is not drawn.
- A mechanism two tools need is an atom with its own row, not code inside one tool (ADR 0118).
- The ruler is a transient atom: no command, no undo, the value at the pointer and in the
  centre zone of the status bar, a new measurement on the third click (U98).
- The niche becomes a tool, and fill is its first consumer (U99).
- The armed tool's parameters live in one card at the pointer and in the inspector, reading one
  draft and committing one command (ADR 0119, U97).
- No moving toolbar: the context menu (U92) and the tool card are the dynamic surfaces. The
  decision is revisited only with a measurement of an action absent from all of them.

## Ruled out

- A generated inventory from the registry alone: it cannot say which context a command belongs
  to or how it should read in the ribbon, and a generated list would make every surface look
  alike while teaching nothing.
- Deriving the ribbon from the table: the ribbon stays a curated lexicon with a stable order;
  the table says where a tool may appear, the map says in which cell and next to what.
- A context menu built by hand next to the tree's: that is the fourth list the table exists to
  prevent (U92 now names U94 as its prerequisite).
- Marking the three orphans as ordinary debt: a command reachable only by typing its id is a
  missing place or a capability meant for the API, and it has to say which.
